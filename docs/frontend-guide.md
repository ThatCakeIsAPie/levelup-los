# Frontend guide

How the LevelUp LOS front end is put together, and the rules for building pages on it. The approved visual design is in [`design/redesign-mockup.html`](design/redesign-mockup.html) (Dashboard and person profile, desktop and phone, light and dark).

## Stack

- Vite + React 19 + TypeScript, single-page app (no server rendering). Capacitor will wrap the same build for iOS and Android later.
- TanStack Router with file-based routes in `src/routes` (flat names: `people.$id.tsx`, `events.index.tsx`). `src/routeTree.gen.ts` is generated by the dev server or build; never edit it. After adding a route, run `npm run dev` or `npm run build` once before `npm run typecheck`.
- Tailwind v4 + shadcn/ui (`src/components/ui`), lucide-react icons, sonner toasts, recharts 3.
- Zustand stores in `src/stores` (and the chat store in `src/data/chat/store.ts`). In the browser-storage demo they persist to `localStorage` (keys `levelup.*`); with real accounts they live in memory and are synced with Supabase (see [Two data sources](#two-data-sources)). **Pages never import stores directly**; they go through `@/data`, whose hooks and writes are the same in both modes.
- Font: Plus Jakarta Sans (`@fontsource-variable/plus-jakarta-sans`, bundled so it works offline).

## Page conventions

- Title: `head: () => ({ meta: [{ title: "People — LevelUp LOS" }] })`. For a title that depends on data, add a `loader` that reads through a non-reactive `@/data` getter and use `head: ({ loaderData }) => ...` (see `people.$id.tsx`, which uses `getPerson`); call `router.invalidate()` after a write that changes it.
- Search params: declare them with the route's `validateSearch` (all optional) so links stay type-checked, e.g. `/events/$id?tab=attendees&filter=no-ticket` opens the Attendees tab showing only people who still need a ticket.
- Export only `Route` from a route file; keep helper components unexported (automatic code splitting).
- `<main id="main">` in the shell is the scroll container and a flex column (the apprentice notice, when shown, sits above the page). Pages render plain content with padding `px-4 py-5 lg:px-[26px] lg:py-[22px]`; a centered `mx-auto max-w-*` page root also needs `w-full`. A full-screen page (the mindmap) uses `flex min-h-0 flex-1 flex-col` on its root to take exactly the space left; never measure offsets or set `h-screen`.
- Every page must work at 375px wide with no horizontal page scroll. Wide tables become card lists on phones (`useIsDesktop()` or responsive classes); only a deliberately wide table may scroll inside its own `overflow-x-auto` box.
- One `<Toaster>` and one `<TooltipProvider>` live in the root; don't add another. Use `Tooltip` (not `title`) for real tooltips, keeping an `sr-only` copy of the text when the trigger isn't focusable. Confirmations use `AlertDialog`, never `window.confirm`.
- Quick logs get an Undo on their toast: `quickCheckIn(personId, message, { note?, description?, onUndo? })` and `toastWithUndo(message, undo)` from `@/components/log/quickLog`.
- Shared costs render with `SharedCostsCard` (`eventId?` for one event, `showPay?`) and `PaySandboxDialog` from `@/components/costs/SharedCosts`, used by the Wallet and the event page. Don't build another cost UI.
- Dates are `"YYYY-MM-DD"` strings. Use `parseDate`, `localDate`, `daysFromToday`, `daysSince` from `@/data`. Never `new Date("YYYY-MM-DD")` (UTC shift) or `toISOString().slice(0, 10)` (UTC date).
- Run `npx prettier --write <files you touched>`, not the whole repo.

## Design tokens (Tailwind classes)

The full list is documented at the top of `src/styles.css`. Light and dark values switch automatically with the `dark` class on `<html>`.

- Surfaces: `bg-app` (page), `bg-surface` (cards), `bg-surface-2` (inset), `border-line`, `bg-track` (progress tracks), `text-faint`; navy event card `bg-event text-event-fg text-event-muted`.
- Primary: `bg-primary text-primary-foreground` (teal), soft: `bg-primary-soft text-primary-ink`. Focus ring is sky.
- Stages: IBO `bg-stage-ibo text-stage-ibo-fg`; Apprentice `bg-stage-apprentice-soft text-stage-apprentice-ink`; Prospect `bg-stage-prospect-soft text-stage-prospect-ink`; Customer `bg-stage-customer-soft text-stage-customer-ink`. ## Data layer — `@/data`

### Two data sources

`src/lib/config.ts` picks the data source at build time (`VITE_DATA_SOURCE`, see `.env.example`); page code is identical in both.

|                                                                                | `local` (GitHub Pages demo, demo picker)                                                              | `supabase` (real accounts)                                                                                                                                                                                           |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stores                                                                         | persisted to `localStorage` (`levelup.*`), seeded from `src/data/seed.ts` and `src/data/chat/seed.ts` | in memory only (`src/stores/storage.ts`); start empty, never read or write the demo keys                                                                                                                             |
| Loading                                                                        | synchronous from `localStorage`                                                                       | after sign-in, `openRemoteSession` loads everything the person may see (RLS filters) before the gate shows the app ("Loading your team…"); sign-out empties the stores                                               |
| Writes                                                                         | the store change is the save                                                                          | the store change shows at once (optimistic) and the sync engine writes it to Postgres; a refused or failed write is rolled back with one toast ("Couldn't save — check your connection and try again") and a re-sync |
| Side effects (notifications, check-in contacts, cascades, activity on deletes) | written by `src/data`                                                                                 | written by the database's triggers and RPCs; the client only shows them (`serverSide`) and never writes them                                                                                                         |
| Other people's changes                                                         | —                                                                                                     | chat tables via Realtime; CRM tables refetched on focus, when the connection returns and every 3 minutes                                                                                                             |
| Chat media                                                                     | IndexedDB (`idb:` paths)                                                                              | private `chat-media` bucket, signed URLs                                                                                                                                                                             |

How the `supabase` mode works (`src/data/remote`):

- `rows.ts` maps each table's snake_case rows to the camelCase store types and back (timestamps normalised to ISO "Z" strings). `bindings.ts` says which store holds which table.
- `engine.ts` keeps a _baseline_ (the rows as the server has them) per table. When a store changes, it diffs the store against the baseline and sends inserts, updates (only the changed columns; one request for the same change on many rows) and deletes through one serial queue: parents before children, deletes children first. RPCs are used where they exist: `pay_sandbox` (payments), `mark_conversation_read` (read state), `create_dm`, `approve_announcement` / `reject_announcement` (with the id the app already shows), `answer_event_post` (RSVP on an event card). Changes from the server (load, refetch, realtime, RPC results) go through `replaceStore` / `applyRemote` / `serverSide`, which update the store _and_ the baseline, so they are never echoed back. A realtime row for something with a write in flight waits until that write finishes.
- `realtime.ts` follows `messages`, `reactions`, `mentions`, `attachments`, `notifications`, `conversation_members`, `conversations`, `announcement_drafts` and `reports` on one channel per person (RLS applies per subscriber). Being added to a chat, a check-in notification and an unknown author trigger a refetch of what they need; a reconnect refetches everything.
- `extras.ts` holds what only the database has: the chat directory (names and roles of chat members outside your CRM view, used by `useChatPeople`, mentions and DM titles) and the team-wide event card totals (`event_rsvp_counts()`, used by `useEventRsvp`). Unread counts and the Events attention badge are computed from the synced rows with the same rules as before.
- Chat media: `saveAttachment(blob)` returns a `pending:` path and shows the file from memory; `sendMessage` uploads it to `chat-media` as `<conversation_id>/<uuid>.<ext>` and only then writes the message and its attachment rows. `useAttachmentUrl` turns stored paths into signed URLs (one hour, renewed a minute early). Seed media (`seed:` paths) is still synthesised.
- `hydrate.ts` (`fetchSnapshot(client, personId)`) and `subscribeChanges(client, …)` take a client, so `npm run test:integration` can run them for several demo users at once.

**Visibility rules** (`src/data/access.ts`, unit-tested): leaders, IBOs and apprentices see themselves plus their business downline, and only customers they own; candidates see only themselves. Everyone sees the event list; attendance is filtered to visible people. A person you can't see behaves as "not found". Pure helpers: `downlineIds`, `visibleIdSet`, `visiblePeople`, `visibleCustomers`, `canSeePerson`, `filterAttendances`, `sponsorChain`, `downlineOf`; type `Viewer`.

**Session**: `useSession()` (nullable), `useCurrentUser()` (non-null inside the shell), `useMe()`, `useViewer()`, `getViewer()`, `login(user)`, `logout()`, `resetDemo()` (clears every `levelup.*` key, reloads at `/login`).

**People**: `useVisibleIds()`, `useVisiblePeople()`, `useVisibleTeam()` (no customers), `usePerson(id)` (undefined if missing or not visible), `useVisibleCustomers()` (by monthly volume), `useCustomersOf(personId)` (only the viewer's own customers), `useCustomerCounts()` (`Record<ownerId, number>` for team totals), `useSponsorChain(personId, max?)` (root-first, stops at the viewer), `useDownline(personId, { directOnly? })`, `getPerson(id)` (like `usePerson`, non-reactive, for route loaders); writes `addPerson`, `updatePerson`, `removePerson`.

`removePerson` cascades (pure rules in `src/data/cascade.ts`): the person's direct downline and the customers they own move to the deleted person's sponsor (so nobody drops out of view); their attendance rows, travel plans, shared-cost memberships, overrides and payments are removed; shared costs they organized pass to that sponsor (who is not opted in). Each moved person gets an activity entry.

**Mind map sync** (used only by `src/components/mindmap/useTreeStore.ts`): `syncPeopleFromLos(entries)`, `getPersonByLosUid(uid)`, pure `syncLosEntries(people, entries)`, type `LosSyncEntry`. Matching (`src/data/losSync.ts`): by `losUid`; else by name only when exactly one business person has it, they have no `losUid` yet and the name appears once in the upload; else a new IBO is created. An existing person is never re-sponsored under someone created from an ambiguous name. Maps drawn from the roster use node uids `roster:<id>` and never sync back (people added on such a map go straight to `addPerson`); uploads use stable per-sheet uids (`sheet:<member id>:<name>`) so re-uploading the same file matches by `losUid`.

**Events**: `useEvents()` (oldest first), `useUpcomingEvents()`, `usePastEvents()`, `useNextEvent(type?)`, `useEvent(id)`, `isUpcoming(e)`, `useAttendancesForEvent(eventId)`, `useAttendancesForPerson(personId)`, `useVisibleAttendances()`, `useEventsAttentionCount()`; writes `addEvent`, `updateEvent`, `removeEvent`, `assignToEvent(eventId, personId)`, `updateAttendance`, `removeAttendance`, `bulkUpdateAttendances(ids, patch)` (logs ticket / attended / no-show activity like single updates). `removeEvent` also removes the event's attendance rows, travel plans, shared costs and their payments. `CrmEvent` has optional `endDate`.

**Needs attention** (one rule, `src/data/attention.ts`): `attentionItems(event, rows)` (one item per person, most urgent first: planned ticket date passed, buying or follow-up due within a week, wants to go with no helper / no follow-up; finished events only flag unrecorded attendance), `upcomingAttentionCount(events, rows)` (sum over unfinished events; the nav badge via `useEventsAttentionCount()`), `needsTicket(a)` (no ticket and not "not going"). The nav badge, the Events list cards, the Dashboard event card and the event page all use these.

**Contacts, sales, learning**: `useContacts(personId?)`, `useLastContactMap()`, `useLastContact(id)`, `useContactSettings()` (`{customerDays: 30, teamDays: 14}`), `useSales(customerId?)`, `useLearning(personId)`, `useTeamLearning()`, `useLearningGoal(personId)` (default 60 pages / 3 podcasts / 1 workshop per week); writes `logContact({personId, byId?, date?, note?})` (returns the `Contact`), `removeContact(id)`, `logLearning({kind, title, amount?, date?, personId?})`, `logSale({customerId, product, date?, amount?})` (returns the `Sale`), `removeSale(id)`, `removeLearning`, `setLearningGoal(personId, patch)`, `setContactSettings(patch)`.

**Activity**: `useActivity(personId)`, `useEventActivity(eventId)`.

**Wallet / ops**: `useSharedCosts(eventId?)`, `useCostSplit(cost)` (each member's current share), `useCostOrganizerName(cost)` ("You", their name when visible, else "a team leader"), `useMyInvoices()`, `useVisibleInvoices()`, `useLogistics(eventId)`, `useMyCampaigns()`, `useMyReportSchedule()`; writes `setLogistics`, `addSharedCost`, `toggleCostOptIn`, `setCostOverride`, `paySandbox`, `addCampaign`, `setReportSchedule`; helpers `splitCost(cost, paid?)`, `invoicesFor`; type `Payment`. Rules: `paySandbox` stores the amount paid and the cost name at payment time (paid invoices show them); a paid share is fixed in the split and can't be overridden; a member who has paid can't opt out; only leaders and IBOs create costs; only the organizer edits shares.

**Re-exported helpers**: `lastContactDate`, `lastSale`, `learningStreak`, `bestLearningStreak`, `learningGoalFor`, `daysSince`, `daysFromToday`, `localDate`, `parseDate`, `bizClassLabel`, `effectiveBizClass`, `apprenticeAlertLevel`, `apprenticeAlertLabel`, `missingRequiredFields`, `DEMO_USERS`, `roleLabel`, `getPersonShowRate`, `getEventFunnel`, `getRiskFlags`, `getUpcomingFollowUps`, `getComparisonEvents(event, events)` (previous same-type event and the one about a year earlier), `getAuditDelta(eventIds, attendances, people, unknownName?)`, `attendanceStatusLabel`, the cascade helpers `rosterWithout`, `opsWithoutPerson`, `opsWithoutEvent`, and the main types (`CrmPerson`, `BizClass`, `CrmEvent`, `Attendance`, …).

In the browser demo writes don't enforce visibility; only reads are filtered. With real accounts row-level security enforces both, and a refused write is rolled back.

**Chat list**: two tabs, Groups (Announcements, Main chat, team groups, side groups) and Direct messages (`chatTab(conversation)`). `useChatTabs()` returns `{ groups, direct, unread }`, each list in order: the viewer's pinned chats first, in the order they pinned them (ties: Announcements, Main chat, then latest message), then the rest by latest message (`sortConversations`). `ConversationSummary` has `tab`, `pinned` and `pinnedAt`. Pins are personal (`ConversationMember.pinnedAt`): `pinConversation(id)` returns `{ ok: true }` or `{ ok: false, reason: "limit" | "not-member" }` (at most `MAX_PINS_PER_TAB` = 10 per tab, `canPinMore`), `unpinConversation(id)`. Team chats start pinned for everyone. The list remembers its tab per viewer in `localStorage` (`levelup.chatTab.<personId>`).

**Team chat ids**: the demo and the local seed use the readable ids in `CHAT_IDS` (`main`, `daily-wins`, …); a real workspace's ids are generated. Use `getTeamChatId("main" | "announcements" | "dailyWins" | "highSignal")` to post into a team chat.

## Hosting

Every push to `main` builds and deploys the app to GitHub Pages via `.github/workflows/pages.yml`: **https://thatcakeisapie.github.io/levelup-los/**. The build sets `BASE_PATH=/levelup-los/`, which Vite uses as `base` and the router uses as `basepath` (`import.meta.env.BASE_URL`), so never hard-code root paths like `"/login"` in plain links or `location` calls — use router `Link`/`navigate`, or prefix with `import.meta.env.BASE_URL`. Pages has no SPA rewrites, so the workflow copies `index.html` to `404.html` to make deep links work on refresh. To build the Pages variant locally in Git Bash, prefix with `MSYS_NO_PATHCONV=1` so the path isn't rewritten.
