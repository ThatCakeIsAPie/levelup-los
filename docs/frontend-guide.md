# Frontend guide

How the LevelUp LOS front end is put together, and the rules for building pages on it. The approved visual design is in [`design/redesign-mockup.html`](design/redesign-mockup.html) (Dashboard and person profile, desktop and phone, light and dark).

## Stack

- Vite + React 19 + TypeScript, single-page app (no server rendering). Capacitor will wrap the same build for iOS and Android later.
- TanStack Router with file-based routes in `src/routes` (flat names: `people.$id.tsx`, `events.index.tsx`). `src/routeTree.gen.ts` is generated by the dev server or build; never edit it. After adding a route, run `npm run dev` or `npm run build` once before `npm run typecheck`.
- Tailwind v4 + shadcn/ui (`src/components/ui`), lucide-react icons, sonner toasts, recharts 3.
- Zustand stores in `src/stores` (and the chat store in `src/data/chat/store.ts`). In the browser-storage demo they persist to `localStorage` (keys `levelup.*`); with real accounts they live in memory and are synced with Supabase (see [Two data sources](#two-data-sources)). **Pages never import stores directly**; they go through `@/data`, whose hooks and writes are the same in both modes.
- Font: Plus Jakarta Sans (`@fontsource-variable/plus-jakarta-sans`, bundled so it works offline).

## Page conventions

- Title: `head: () => ({ meta: [{ title: "People — LevelUp LOS" }] })`. For a title that depends on data, add a `loader` that reads through a non-reactive `@/data` getter and use `head: ({ loaderData }) => ...` (see `people.$id.tsx`, which uses `getPerson`); call `router.invalidate()` after a write that changes it.
- Search params: declare them with the route's `validateSearch` (all optional) so links stay type-checked, e.g. `/events/$id?tab=attendees&filter=no-ticket` opens the Attendees tab showing only people who still need a ticket. Multi-select filters keep a list as one comma-separated param (`?stage=apprentice,ibo`) with `parseListParam(raw, allowed)`, `listParam(list)` and `toggleInList` from `@/lib/searchList` (values that may contain commas, like locations, use a list param instead). Stage filters use `StageFilterChips` (`@/components/filters/StageFilterChips`: "All" plus one chip per stage with counts; several can be on, none = everyone).
- Export only `Route` from a route file; keep helper components unexported (automatic code splitting).
- `<main id="main">` in the shell is the scroll container and a flex column (the apprentice notice, when shown, sits above the page). Pages render plain content with padding `px-4 py-5 lg:px-[26px] lg:py-[22px]`; a centered `mx-auto max-w-*` page root also needs `w-full`. A full-screen page (the mindmap) uses `flex min-h-0 flex-1 flex-col` on its root to take exactly the space left; never measure offsets or set `h-screen`.
- Every page must work at 375px wide with no horizontal page scroll. Wide tables become card lists on phones (`useIsDesktop()` or responsive classes); only a deliberately wide table may scroll inside its own `overflow-x-auto` box.
- One `<Toaster>` and one `<TooltipProvider>` live in the root; don't add another. Use `Tooltip` (not `title`) for real tooltips, keeping an `sr-only` copy of the text when the trigger isn't focusable. Confirmations use `AlertDialog`, never `window.confirm`.
- Quick logs get an Undo on their toast: `quickCheckIn(personId, message, { note?, description?, onUndo? })` and `toastWithUndo(message, undo)` from `@/components/log/quickLog`.
- Shared costs render with `SharedCostsCard` (`eventId?` for one event, `showPay?`) and `PaySandboxDialog` from `@/components/costs/SharedCosts`, used by the Wallet and the event page. Don't build another cost UI.
- Dates are `"YYYY-MM-DD"` strings. Use `parseDate`, `localDate`, `daysFromToday`, `daysSince` from `@/data`. Never `new Date("YYYY-MM-DD")` (UTC shift) or `toISOString().slice(0, 10)` (UTC date).
- **Breadcrumbs**: a page reached from another page (a person, an event, a library item, a settings subpage) shows the trail at the top, where a back link would be: `PageHeader crumbs={[...]}` or `<Breadcrumbs items={[...]} />` (`@/components/brand`), e.g. "People › Anita Patel", "Events › Fall Leadership Weekend", "Library › All talks › Talk". The last crumb is the current page (no `link`). Always one line; on phones a trail of three or more folds the earlier steps into a "…" menu. Don't hand-roll a "‹ Back" link.
- **Log button**: one, in the shell (top right on desktop in the slim top bar, the round + in the middle of the phone tab bar). Pages never add their own.
- **Phone numbers**: type them in `PhoneInput` (`@/components/brand`, `value` + `onValueChange`), which formats as you type, US style "(512) 555-0102" (+1 and other country codes accepted; an international number keeps its own grouping). Pure helpers in `src/lib/phone.ts` (tested): `formatPhone` (as you type), `normalizePhone` (the stored form; `addPerson`, `updatePerson` and the list entry writes apply it), `displayPhone` (shows older stored numbers the same way), `phoneHref` (for `tel:` / `sms:`).
- **Hot / Warm / Cold**: every form that adds a new contact (Add prospect, Add names / Add someone, the Log sheet's New contact, Add person for a prospect) has the same `RatingPicker` ("How warm are they?", tap the selected one again to clear); cards and rows show `RatingChip`. See [Hot / Warm / Cold](#hot--warm--cold) for the data.
- Run `npx prettier --write <files you touched>`, not the whole repo.

## Data layer — `@/data`

### Two data sources

`src/lib/config.ts` picks the data source at build time (`VITE_DATA_SOURCE`, see `.env.example`); page code is identical in both.

|                                                                                | `local` (GitHub Pages demo, demo picker)                                                              | `supabase` (real accounts)                                                                                                                                                                                           |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stores                                                                         | persisted to `localStorage` (`levelup.*`), seeded from `src/data/seed.ts` and `src/data/chat/seed.ts` | in memory only (`src/stores/storage.ts`); start empty, never read or write the demo keys                                                                                                                             |
| Loading                                                                        | synchronous from `localStorage`                                                                       | after sign-in, `openRemoteSession` loads everything the person may see (RLS filters) before the gate shows the app ("Loading your team…"); sign-out empties the stores                                               |
| Writes                                                                         | the store change is the save                                                                          | the store change shows at once (optimistic) and the sync engine writes it to Postgres; a refused or failed write is rolled back with one toast ("Couldn't save — check your connection and try again") and a re-sync |
| Side effects (notifications, check-in contacts, cascades, activity on deletes) | written by `src/data`                                                                                 | written by the database's triggers and RPCs; the client only shows them (`serverSide`) and never writes them                                                                                                         |
| Other people's changes                                                         | —                                                                                                     | chat tables via Realtime; CRM tables refetched on focus, when the connection returns and every 3 minutes                                                                                                             |
| Chat media                                                                     | IndexedDB (`idb:` paths)                                                                              | private `chat-media` bucket, signed URLs                                                                                                                                                                             |

How the `supabase` mode works (`src/data/remote`):

- `rows.ts` maps each table's snake_case rows to the camelCase store types and back (timestamps normalised to ISO "Z" strings). `bindings.ts` says which store holds which table.
- `engine.ts` keeps a _baseline_ (the rows as the server has them) per table. When a store changes, it diffs the store against the baseline and sends inserts, updates (only the changed columns; one request for the same change on many rows) and deletes through one serial queue: parents before children, deletes children first. RPCs are used where they exist: `pay_sandbox` (payments), `mark_conversation_read` (read state), `create_dm`, `approve_announcement` / `reject_announcement` (with the id the app already shows), `answer_event_post` (RSVP on an event card); `merge_event_categories` is called directly by `mergeEventCategories` (moves the events and archives the category in one step; the client shows it with `serverSide`). Changes from the server (load, refetch, realtime, RPC results) go through `replaceStore` / `applyRemote` / `serverSide`, which update the store _and_ the baseline, so they are never echoed back. A realtime row for something with a write in flight waits until that write finishes. Deletes are never inferred from a row being missing: only rows a mutation removed are deleted, a change that empties a whole table is never sent as deletes, and a server row for something being deleted is dropped. Switching people (sign-out, or another tab of the same browser signing someone else in) stops the engine at once, before the stores are emptied and the next person is loaded, and a batch still being sent stops there. The dev server never hot-swaps `engine.ts` or `remote/index.ts`: editing them reloads the page (two engine copies on the same stores used to send each other's loads as deletes).
- `realtime.ts` follows `messages`, `reactions`, `mentions`, `attachments`, `notifications`, `conversation_members`, `conversations`, `announcement_drafts` and `reports` on one channel per person (RLS applies per subscriber). Being added to a chat, a check-in notification and an unknown author trigger a refetch of what they need; a reconnect refetches everything.
- `extras.ts` holds what only the database has: the chat directory (names and roles of chat members outside your CRM view, used by `useChatPeople`, mentions and DM titles) and the team-wide event card totals (`event_rsvp_counts()`, used by `useEventRsvp`). Unread counts and the Events attention badge are computed from the synced rows with the same rules as before.
- Chat media: `saveAttachment(blob)` returns a `pending:` path and shows the file from memory; `sendMessage` uploads it to `chat-media` as `<conversation_id>/<uuid>.<ext>` and only then writes the message and its attachment rows. `useAttachmentUrl` turns stored paths into signed URLs (one hour, renewed a minute early). Seed media (`seed:` paths) is still synthesised.
- `hydrate.ts` (`fetchSnapshot(client, personId)`) and `subscribeChanges(client, …)` take a client, so `npm run test:integration` can run them for several demo users at once.

**Visibility rules** (`src/data/access.ts`, unit-tested): leaders, IBOs and apprentices see themselves plus their business downline, and only customers they own; candidates see only themselves. A leader's deputy (`Viewer.deputyOf`, filled in by `useViewer()` / `getViewer()` from the deputies) also sees the leader and the leader's business downline, never the leader's customers. Everyone sees the event list; attendance is filtered to visible people. A person you can't see behaves as "not found". Pure helpers: `downlineIds`, `visibleIdSet`, `visiblePeople`, `visibleCustomers`, `canSeePerson`, `filterAttendances`, `sponsorChain`, `downlineOf`; type `Viewer`.

**Session**: `useSession()` (nullable), `useCurrentUser()` (non-null inside the shell), `useMe()`, `useViewer()`, `getViewer()`, `login(user)`, `logout()`, `resetDemo()` (clears every `levelup.*` key, reloads at `/login`).

**People**: `useVisibleIds()`, `useVisiblePeople()`, `useVisibleTeam()` (no customers), `usePerson(id)` (undefined if missing or not visible), `useVisibleCustomers()` (by monthly volume), `useCustomersOf(personId)` (only the viewer's own customers), `useCustomerCounts()` (`Record<ownerId, number>` for team totals), `useSponsorChain(personId, max?)` (root-first, stops at the viewer), `useDownline(personId, { directOnly? })`, `getPerson(id)` (like `usePerson`, non-reactive, for route loaders); writes `addPerson`, `updatePerson`, `updatePeople(changes)` (bulk patches; returns an undo that restores exactly the changed fields and the stage history, so an undone stage change doesn't count as a registration), `removePerson`.

**People list** (`/people`, `src/modules/people-list`; pure rules in `model.ts`, tested in `model.test.ts`): filters live in the URL (`?seg=customers`, `q`, `stage=apprentice,ibo`, `attn=contact,missing` or `attn=any`, `loc` (list), `sort`; `validatePeopleSearch`, `filtersFromSearch`, `searchFromFilters`). Stages, attention reasons and locations are multi-select (`filterRows`, `stageCounts`, `attentionCounts`, `toggleAttention`). Selection: checkboxes and the header "select all shown" on desktop; on phones "Select" (or a long press on a card) starts select mode with "Select all". Never yourself (`toggleAllShown`, `shownSelection`, `selectedShown`). The `BulkBar` does check-in, add to an upcoming event, export and, under More: change stage and change sponsor (business people only), add a tag, set a follow-up date, delete. Each action works out who it applies to and why others are skipped (`stageChangePlan`: no one becomes a prospect while they have people under them; `sponsorChoices` / `sponsorChangePlan`: apprentices and IBOs only, never into the person's own downline; `tagPlan`; `deletePlan`: never yourself or anyone above you, the same as row-level security for a deputy's leader). Changes get one Undo toast (`updatePeople`, removing the added attendance rows or contacts); delete asks first and can't be undone.

`removePerson` cascades (pure rules in `src/data/cascade.ts`): the person's direct downline and the customers they own move to the deleted person's sponsor (so nobody drops out of view); their attendance rows, travel plans, shared-cost memberships, overrides and payments are removed; shared costs they organized pass to that sponsor (who is not opted in). Each moved person gets an activity entry.

**Mind map sync** (used only by `src/components/mindmap/useTreeStore.ts`): `syncPeopleFromLos(entries)`, `getPersonByLosUid(uid)`, pure `syncLosEntries(people, entries)`, type `LosSyncEntry`. Matching (`src/data/losSync.ts`): by `losUid`; else by name only when exactly one business person has it, they have no `losUid` yet and the name appears once in the upload; else a new IBO is created. An existing person is never re-sponsored under someone created from an ambiguous name. Maps drawn from the roster use node uids `roster:<id>` and never sync back (people added on such a map go straight to `addPerson`); uploads use stable per-sheet uids (`sheet:<member id>:<name>`) so re-uploading the same file matches by `losUid`.

**Events**: `useEvents()` (oldest first), `useUpcomingEvents()`, `usePastEvents()`, `useNextEvent(categoryId?)`, `useEvent(id)`, `isUpcoming(e)`, `useAttendancesForEvent(eventId)`, `useAttendancesForPerson(personId)`, `useVisibleAttendances()`, `useEventsAttentionCount()`; writes `addEvent`, `updateEvent`, `removeEvent`, `assignToEvent(eventId, personId)`, `updateAttendance`, `removeAttendance`, `bulkUpdateAttendances(ids, patch)` (logs ticket / attended / no-show activity like single updates). `removeEvent` also removes the event's attendance rows, travel plans, shared costs and their payments. `CrmEvent` has `categoryId` (its event category, below) and optional `endDate` and `format`; `Attendance.mode` is `"in_person" | "virtual"` (the ticket's type, or how they came; it used to be `ticketType` with `"stream"`).

**Needs attention** (one rule, `src/data/attention.ts`): `attentionItems(event, rows)` (`event` is an `AttentionEvent`: its days plus `tickets`, whether its category uses tickets, `{ ...e, tickets: usesTickets(categoryOf(e)) }`; one item per person, most urgent first: planned ticket date passed, buying or follow-up due within a week, wants to go with no helper / no follow-up; finished events only flag unrecorded attendance), `upcomingAttentionCount(events, rows)` (the same `AttentionEvent`s with ids; sum over unfinished events; the nav badge via `useEventsAttentionCount()`), `needsTicket(a)` (no ticket and not "not going"). The nav badge, the Events list cards, the Dashboard event card and the event page all use these. Events without tickets (below) only flag follow-ups that are due.

**Event categories, attendance and missed-event follow-ups** (`src/data/eventCategories` for the categories, `src/data/eventTypes` for formats, attendance and missed events; UI in `src/modules/events`; plan: [`plans/mvp-plan-2026-10-13.md`](plans/mvp-plan-2026-10-13.md) "Events"):

- **Event categories** replace the six fixed types: each team keeps its own list (`EventCategory`: `id`, `name`, `icon` from the curated `CATEGORY_ICONS` (lucide, mapped in `src/modules/events/categoryIcons.ts`; unknown keys show a calendar), `tone` (`CATEGORY_TONES`: neutral, green, blue, amber, rose on the tone tokens), the settings `allowsVirtual`, `usesTickets`, `usesTravel`, `countsForMissed`, `welcomesCustomers`, `position`, `archivedAt`, `createdBy`, `createdAt`). Every team starts with the six old types (`STARTING_CATEGORIES`, ids `<workspace>-<old type>`, e.g. `w1-night_owls`, the same in the demo, the database seed and every new workspace): Night Owls and Work session (in person), Info session and Training (online too, customers welcome), Monthly team meeting (online, tickets, customers welcome), Conference (online, tickets, travel); all six remind uplines about misses. What used to come from the type comes from the category's settings: `allowsVirtual(c)`, `usesTickets(c)`, `usesTravel(c)`, `welcomesCustomers(c)`, `countsForMissed(c)` (unknown counts). `CrmEvent.format` is `"in_person" | "virtual" | "both"`; read it with `eventFormat(e, category)` (in person unless set, never virtual for an in-person-only category) and `eventModes(e, category)`. Labels `EVENT_FORMAT_LABEL`, `MODE_LABEL`; `categorySummary(c)` ("In person or online · Tickets").
- Category hooks (`@/data`): `useEventCategories()` (active ones, in order: the picker and the Events filter), `useAllEventCategories()` (archived too), `useCategoryOf()` (a lookup `(event | id) => EventCategory`, `UNKNOWN_CATEGORY` when missing; re-renders when categories change: use it in lists), `useEventCategory(event)`, non-reactive `eventCategory(event)` / `getEventCategories()`, `useCategoryEventCounts()`, `useCanCreateCategories()` (= `useCanManageEvents()`), `useCanEditCategories()` (leaders and their deputies). Writes: `addEventCategory({ name, icon, tone?, ...flags })` → `{ ok, category } | { ok: false, error }` (names are unique among active categories, any case, `categoryNameError`), `updateEventCategory(id, patch)` (error or null), `reorderEventCategories(ids)`, `archiveEventCategory(id)` (returns an undo), `restoreEventCategory(id)`, `mergeEventCategories(fromId, intoId)` (every event moves over, a format the target doesn't allow becomes in person, then the first is archived; real accounts: one `merge_event_categories()` call, shown at once and rolled back if refused). Pure rules in `src/data/eventCategories/rules.ts` (tested in `rules.test.ts`): `activeCategories`, `sortCategories`, `categoryLookup`, `categoryChoices(list, currentId)` (active, plus an event's own archived one when editing it), `mergeError`, `mergeEvents`, `reorderPatches`, `nextPosition`, `canEditCategories`, `canCreateCategories`, `convertLegacyEvent(s)` (saved demo events with a `type` get its starting category on load; `team_meeting` and unknown types become the monthly meeting), `categoryForLegacyType` (old `?type=` links).
- Archived categories stay on their old events (chip, filters, follow-ups) and can be brought back; they aren't offered for new events, and an event can't be moved into one. Categories are never deleted.
- **Who may plan events:** `canManageEvents(viewer)` / `useCanManageEvents()` is the one check (pages, the Log sheet, "+ New category" in the event form). Leaders, deputies, the admin and 3/10 and up.
- Event page: the category's settings decide it: travel keeps tickets, travel, shared costs, qualifications and the attendee board (the Conference); tickets keep the ticket board without a travel tab (the monthly meeting); the rest get a light Overview: "Who's coming" (Coming / Maybe / Can't) before the day and "Who came" (In person / Virtual / Not there, one tap each, `SimpleRoster`) from the event day, plus `MyAttendanceCard` for the viewer. The attendee views (Attendees tab table, cards and board, and `SimpleRoster`) filter by kind of person with `?stage=apprentice,ibo,customer,prospect` (multi-select chips, none = everyone, by `effectiveBizClass`; the Customer chip shows only when the list has customers; pure helpers in `src/modules/events/stageFilter.ts`). The navy feature card (Events list, Home, My business) is the next event whose category has travel.
- Events list: "All" plus one chip per active category (hidden scrollbar on phones), `/events?category=<id>`; old `?type=night_owls` links show that starting category. The form (`EventFormDialog`) has one category picker (`CategoryPicker`: a searchable list with each category's icon and settings) and, for people who may plan events, "+ New category" (name, icon and "Can people join online?", "Do people buy tickets?", "Is there travel?", "Remind uplines when someone misses one?"; `CategoryFields`); then in person / virtual / both (where the category allows it), and it can repeat a new event weekly (up to 12 weeks). Chips and tiles: `EventCategoryChip`, `EventFormatChip`, `CategoryTile` (`src/modules/events/categoryMeta.tsx`).
- Team settings (`/settings/team`, leaders and deputies): **Event categories** card (`EventCategoriesCard`): one row per active category (drag the handle or use the arrow keys to reorder, saved on release; edit opens name, icon, color and all five settings, including "Are customers welcome?"), Add, ⋯ → "Merge into another…" (confirm dialog: how many events move, what the target's settings mean for them, can't be undone) and "Archive" (Undo on the toast); "Archived (N)" lists archived ones with "Bring back".
- Editing attendees: every field shown is editable and clearable where it makes sense. The attendee sheet (`AttendeeEditSheet`), the profile's event dialog (`AttendanceDialog`) and the table and board selects all offer "Not asked" for wants to go; optional dates use `ClearableDate` (`src/modules/events`). A person's profile has "Create event" on its Events card and tab (only when `useCanManageEvents()`): the usual `EventFormDialog`, then the person is added to the new event. Deleting a person is in the profile's ⋯ menu (`DeletePersonDialog` in `src/modules/people/DetailsTab.tsx`, with the same confirmation), not on the Details tab.
- Attendance: `setEventAttendance(eventId, personId, mode | false | null)` (adds them to the list if needed; returns an undo). **Growth path** (`src/data/growth`, UI in `src/modules/growth`; plan: [`plans/mvp-plan-2026-10-13.md`](plans/mvp-plan-2026-10-13.md) "Growth path"): the 13 milestones from New apprentice to 12/100 (`GROWTH_MILESTONES`, codes `GrowthMilestoneCode`: `new_apprentice`, `first_sale`, `core_150`, `core_300`, `first_sponsor`, `bronze_foundation`, `3_10`, `bronze_builder`, `6_25`, `6_50`, `platinum`, `ruby`, `12_100`; `growthLabel(code)`). Each has a hold class (`GrowthMilestoneDef.hold`, `growthHold(code)`) that says how long it counts once met:

- **Permanent** (`permanent`: New apprentice, First sale, First sponsor): once reached, it stays.
- **Live** (`live`: the headcount milestones 3/10, 6/25, 6/50, 12/100): held only while the current numbers meet it (current personal sponsors and current registered people in the group). Dropping below un-holds it; it becomes one to earn again.
- **Monthly** (`monthly`: the volume milestones Core 150, Core 300, Bronze foundation, Bronze builder, 7,500 Platinum, Ruby): held on a day when the rule was met in that calendar month or the month before. Met in September, it's held through October 31 and gone on November 1 unless met again in November.
- **History is kept apart from "held"**: every milestone keeps the first day it was ever reached (`firstReachedOn`, with `daysTaken` from the previous one) and, for live and monthly ones, the last time it was met (`lastMetOn`). So a milestone is in one of three states (`MilestoneStatus.state`): `held` (checked), `lost` (earned before but not held now: a hollow dot with a history badge, "Hit Dec 2024", "First hit Dec 2024 · earn it again") or `never`. Monthly PV history comes from the PV on record; the count milestones (First sponsor and the headcount ones), which the sponsor tree can forget, are recorded by the app while the data shows them (`MilestoneHistory`, store `milestoneHistory`, table `milestone_history`): `useRecordMilestoneHistory()` in the shell calls `recordMilestoneHistory()` for you and everyone you coach, writing only what's new (a first sighting, an earlier first day, or a last-met day from an earlier month; pure: `historyUpdates(input, ids, today)`).
- **Hand marks** (`MilestoneMark`, set by uplines) record the day a milestone was first reached. On a permanent milestone a mark counts as reached; on a live or monthly one it's history only and never makes it held (monthly PV set by an upline already covers volume). The upline's button says "Record when they first hit it" there.
- **Next milestone** = the first one in path order not held now (`next`, `nextIndex`); later ones held out of order (Platinum held through last month while 6/50 isn't) still show as held. `workingDays` is null when `next` is being earned again. `keepUp` lists monthly milestones held only through last month: the heads-up "Ruby: hit 15,000 group PV again this month to keep it (6,883 so far)" on Home, your profile and, for uplines, a downline's path (`KeepUpNote`).
- **Unlocks go by "ever reached"**: `hasEverReached(personId, code)` (`hasEverReachedMilestone` in the engine) is what `src/data/team/hooks.ts` feeds `computeUnlocks`, so someone who drops below 3/10 keeps event planning. `isHeld(personId, code)` / `useIsHeld` (`isMilestoneHeld`) and the path's `held` / `state` are for display. (`hasReached` is gone, so no caller keeps the old meaning by accident.)
- Where PV comes from: `Sale.pv`, credited to `Sale.personId` (whose PV it is: the customer's owner, or the buyer for a personal order where `customerId` is a business person; older sales without it use the same rule, `saleSellerId`). An upline can set a downline's PV for a calendar month (`PvOverride`, store `pvOverrides`), which replaces that month's logged total; hand marks (`MilestoneMark`, store `milestoneMarks`) record a milestone reached on a day. Both are kept in the CRM store and record who and when.
- Engine (pure, `engine.ts`, tested in `engine.test.ts` and `seed.test.ts`): `growthPath(input, personId, today)` → `GrowthPath` (`milestones[]` with `hold`, `state`, `held`, `firstReachedOn`, `source` `"auto" | "manual"` (of the first date), `autoOn`, `mark`, `lastMetOn`, `heldVia` (`"this_month" | "last_month"`, monthly ones) and `heldUntil`, `daysTaken` from the previous first-reached one, and `progress` for milestones not held and monthly ones held only through last month: `parts` like "95 / 150", `summary`, `best` month, `legs`; plus `next`, `nextIndex`, `latest` (furthest held), `workingDays`, `keepUp`, `thisMonth` {pv, groupPv, override, daysLeft}). `GrowthInput` takes `history` (optional). Rules: PV per calendar month; group PV = your PV plus your whole downline's (`GROUP_PV_INCLUDES_OWN`); a leg = one frontline person's whole line; people counts = registered (apprentice/IBO) people in your downline, not you; held per hold class (above). Dates: the day the month's running total crossed the line (an upline's month figure counts from the day it was set, or the month's last day; nothing counts ahead of today); count rules use the registration date (`registeredOn`: business start date, else stage history, else joined date) of the person who completed it; never before the person registered. Month helpers: `addMonths(month, n)`, `lastDayOf(month)`. `teamStructure(people, personId, { includeProspects? })` → `{ frontline, total }` is the same headcount as a number pair (tested in `structure.test.ts` against the path's counts).
- Team map (`/mindmap`): the header shows the structure as "frontline/total" in the milestone notation ("6/43": 6 registered personal sponsors, 43 registered people in the group, not counting the person; a tooltip says so). Tapping a card shows that person's numbers ("Back to you" returns). "Include prospects" (off by default, remembered per viewer in `levelup.mindmap.prospects.<personId>`) also draws prospects and counts them, labelled "with prospects" so it isn't read as a milestone number; a prospect with someone under them always stays on the map. An uploaded spreadsheet has no stages, so its numbers count everyone in it.
- Hooks: `useGrowthPath(personId)`, `useMyGrowthPath()`, `useHasEverReached(personId, code)`, `useIsHeld(personId, code)`, `useMonthPv(personId, month)` ({logged, override, pv}), `useCanCoach(personId)` (the viewer is an upline), `useRecordMilestoneHistory()` (mounted once in the shell). ## Hosting

Every push to `main` builds and deploys the app to GitHub Pages via `.github/workflows/pages.yml`: **https://thatcakeisapie.github.io/levelup-los/**. The build sets `BASE_PATH=/levelup-los/`, which Vite uses as `base` and the router uses as `basepath` (`import.meta.env.BASE_URL`), so never hard-code root paths like `"/login"` in plain links or `location` calls — use router `Link`/`navigate`, or prefix with `import.meta.env.BASE_URL`. Pages has no SPA rewrites, so the workflow copies `index.html` to `404.html` to make deep links work on refresh. To build the Pages variant locally in Git Bash, prefix with `MSYS_NO_PATHCONV=1` so the path isn't rewritten.
