# Backend (Supabase)

The database for the app: Postgres with row-level security (RLS), auth, storage and realtime, run locally with the Supabase CLI in Docker. It holds all the app's data: the CRM (people, events, attendance, travel, shared costs, contacts, sales, learning, activity, campaigns) and chat. The agreed plan is [`plans/messaging-and-backend-plan-2026-10-12.md`](plans/messaging-and-backend-plan-2026-10-12.md); its "Chat data contract" is implemented field for field.

The GitHub Pages demo does not use any of this: it keeps running on browser storage (`VITE_DATA_SOURCE=local`). With `VITE_DATA_SOURCE=supabase` the app loads everything from here after sign-in and writes every change back (see [Run the app against the local database](#run-the-app-against-the-local-database) and the frontend guide's "Two data sources").

## Run it locally

Needs Docker Desktop running. Everything else comes from `npm install` (the `supabase` CLI and `tsx` are devDependencies).

| Command                    | What it does                                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `npm run db:start`         | Start the local stack (first run pulls the Docker images).                                                                                             |
| `npm run db:stop`          | Stop it. Data is kept in Docker volumes.                                                                                                               |
| `npm run db:reset`         | Regenerate `supabase/seed.sql`, then drop and recreate the database: all migrations plus the seed. Dates are relative to the moment you run it.        |
| `npm run db:seed`          | Only regenerate `supabase/seed.sql` and `supabase/tests/001_visibility_parity.test.sql` from the TypeScript seeds.                                     |
| `npm run db:test`          | Run the pgTAP tests in `supabase/tests` against the running database.                                                                                  |
| `npm run db:types`         | Regenerate `src/data/remote/database.types.ts` from the running database. Run it after changing a migration.                                           |
| `npm run test:integration` | The app's sync layer against the running, seeded database (sign-in as the demo users, load, write-through, realtime, storage). Not part of `npm test`. |

Local endpoints (the CLI's default ports):

| Service                                       | URL                                                       |
| --------------------------------------------- | --------------------------------------------------------- |
| API (REST, auth, realtime, storage via Kong)  | http://127.0.0.1:54321                                    |
| Postgres                                      | `postgresql://postgres:postgres@127.0.0.1:54322/postgres` |
| Mailpit (catches magic-link and invite email) | http://127.0.0.1:54324                                    |

`npx supabase status` prints the local anon key (the CLI's public development key, the same on every machine). Put it in `.env.local` (gitignored), as shown in `.env.example`:

```
VITE_DATA_SOURCE=supabase
VITE_SUPABASE_URL=http://127.0.0.1:54321
VITE_SUPABASE_ANON_KEY=<ANON_KEY from npx supabase status>
```

### A slimmed stack

To keep memory use low (about 0.6–0.7 GB in total), `supabase/config.toml` runs only what the app needs:

- **On:** Postgres (`db`), auth (GoTrue), REST (PostgREST), realtime, storage, Kong (the API gateway) and Mailpit (local email).
- **Off:** Studio, analytics (Logflare and Vector), the edge-functions runtime, imgproxy (storage image transformation), storage's S3 protocol and vector buckets, and the connection pooler.

To browse tables, connect any Postgres client to port 54322, or set `[studio] enabled = true` and restart. `npm run db:test` runs a short-lived `pg_prove` container, and `npm run db:types` runs a short-lived `postgres-meta` container.

Auth config: email sign-in with magic link and with password, and no email confirmation locally. `site_url` is http://localhost:5173, and redirects are allowed for http://localhost:5173 through 5190.

### Run the app against the local database

1. `npm run db:start` (Docker Desktop running), then `npm run db:reset` for a fresh seed (dates are relative to now).
2. `.env.local` needs `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` (above). It may keep `VITE_DATA_SOURCE=local` for the demo; override it per run instead:
   ```
   VITE_DATA_SOURCE=supabase npm run dev -- --port 5180 --strictPort --host localhost
   ```
   (PowerShell: `$env:VITE_DATA_SOURCE="supabase"; npm run dev -- --port 5180 --strictPort --host localhost`.)
3. Open http://localhost:5180/login and pick a demo account (development builds list them; password `demo-local`), or use a magic link from Mailpit. "Loading your team…" shows while the person's data loads.
4. To see live chat, sign in as a second person in another browser profile (or a private window): the two can't share one browser profile, because the session is kept in `localStorage`.

Nothing is written to the demo's `<prefix>.*` storage keys in this mode, so switching `VITE_DATA_SOURCE` back and forth never mixes demo and real data.

Conventions:

- Column names are the snake_case of the TypeScript fields (`sponsorId` is `sponsor_id`).
- Entity ids are `text` (`gen_random_uuid()::text` by default), so client-generated UUIDs and the seed's readable ids (`"1"`, `"c8"`, `"e1"`, `"hs3"`) both work.
- Every CRM table has `workspace_id`, which defaults to the caller's workspace, so clients don't send it. Chat child tables follow the contract exactly and reach their workspace through their conversation or person. Only `conversations`, `members` and `library_items` carry `workspace_id`.
- Columns that default to "who is calling" (`by_id`, `author_id`, `created_by`, `owner_id`, `reporter_id`, `blocker_id`, `person_id` on `reactions`/`learning`/`contact_settings`) are filled with `current_person_id()` when omitted.

### Renameable pipeline stages

Both pipelines have four fixed top-level stages (recruiting: `contact`, `first_meeting`, `first_plan`, `registered`; customer: `contact`, `first_meeting`, `first_sale`, `on_ditto`). Their meaning, order and behaviour never change; each person can only change the **name** they (and their downline) see. Migration `20261017000100_stage_names.sql`, pgTAP `027_stage_names`, client in `src/data/stageNames`.

- **Table `stage_names`**: `person_id`, `workspace_id`, `pipeline` (`recruiting` / `customer`), `stage_key`, `name`, `updated_at`; primary key (`person_id`, `pipeline`, `stage_key`), so one row per person, pipeline and stage. No row means "not set by me". A check refuses a `stage_key` that isn't one of that pipeline's four, and a `name` that isn't trimmed, 1 to 30 characters, without line breaks.
- **RLS**: you read, insert, update and delete only your own rows (in your workspace; candidates have no pipeline and can't insert). Nobody reads an upline's or a downline's rows.
- **The rule** (the same in the browser demo, `resolveStageNames` in `src/data/stageNames/rules.ts`): the name a viewer sees for a stage is, per pipeline and per stage independently, their own name; else the name of the nearest person above them in the sponsor line who set one; else the app's built-in name (the database stores none). A downline's own name is never overridden by an upline's later change, and the person below a downline inherits that downline's name, not a higher one.
- **Function `effective_stage_names(p_include_own boolean default true)`** (`SECURITY DEFINER`, signed-in people only): for the caller, one row per pipeline and stage that has a custom name in their sponsor line: `name`, `from_person_id`, `from_person_name` (the person it comes from, even when you can't read their profile) and `depth` (0 = you, 1 = your sponsor, …). The walk stays in the caller's workspace, never visits a person twice (a cycle ends it) and stops after 50 people. `false` leaves your own rows out: what you would inherit if you cleared yours.
- **Client**: your own rows sync like any other table (`stageNamesBinding`, one upsert or delete per changed row). The names set above you are fetched with `effective_stage_names(false)` along with the pipeline tables, so an upline's change reaches the downline on the next load, focus, reconnect or 3-minute refresh (no realtime).

### Inviting an existing person

A person added as a record first (no login) can be given one without a duplicate. Migration `20261018000100_invite_existing_person.sql`, pgTAP `028_invite_existing_person`, integration test `inviteExistingPerson.test.ts`, client in `src/modules/invites`.

- **Table `invites`**: new nullable `person_id` (references `people`, cascades). A trigger fills `sponsor_person_id`, `stage` and `name` from the person (whatever the client sends is replaced), so a person with no sponsor gives an invite with none (`sponsor_person_id` is nullable; a check wants a sponsor or a person). A person-bound invite must have an `email`: the address the inviter confirmed.
- **One open invite per person**: a unique index on `person_id` where the invite is unused, and the same trigger deletes the person's previous unused invite when a new one is created ("Send again"). Expired unused invites are replaced the same way. Used invites stay as history.
- **Who may create one**: `can_invite_person()`, in the insert policy "invite an existing person" (the ordinary-invite policy now only applies when `person_id` is null). The database has no rule about the person's stage; the app offers the button for apprentices and IBOs only.
- **Has a login** means a `members` row with `user_id` not null. People added in the app (and prospects) have no `members` row at all; seeded apprentices and IBOs have one with `user_id` null. Accepting updates the row or inserts it (role `member`; the team-chat trigger then adds them to the team chats).
- **Accepting** (`accept_invite`): the usual checks (not found, used, expired, already a member), then for a person invite: the person still exists in that workspace and still has no login; the account's email is confirmed and equals the invite's email, ignoring case (a leaked link does not let another account claim the record). Then it attaches the user, fills an empty `people.email` from the invite, marks the invite used and writes the `Joined from an invite link` activity entry. Nothing else of the person changes.
- **Undoing a registration** (the person goes back to prospect) withdraws their unused invite (trigger on `people`).
- **Sending the email**: the inviting browser calls `signInWithOtp` with `shouldCreateUser: true` and `emailRedirectTo` = `/auth/callback?invite=<token>`, on a separate client that uses the implicit flow and keeps no session (`src/modules/invites/emailLink.ts`). The app's own client uses PKCE, whose link only works in the browser that asked for it, which would break an email requested by someone else; the implicit link carries the session in the URL fragment, which `/auth/callback` turns into a session before opening the invite page. The inviter's session and storage are untouched. The built-in mail sender is rate-limited: when sending fails, the app still shows the invite link to share.
- **Demo**: invites live under `<prefix>.personInvites` in the browser (cleared by "Reset demo data"); no email is sent and there is no accept step.

### Repeating events

An event can repeat with no end, the way calendar apps do it. Migration `20261020000100_recurring_events.sql`, pgTAP `030_event_series`, integration test `eventSeries.test.ts`, client in `src/data/recurrence` (frontend guide: "Repeating events").

- **Every occurrence is a real event** (its own id, attendance, answers, roster, follow-ups, chat posts), so everything that hangs off an event keeps working per session. `event_series` holds the rule (`freq`: daily, weekly, biweekly, monthly_date, monthly_weekday; `starts_on`; `ends_on`; `skipped`, the dates deleted on their own) and the template a new occurrence is made from; `events.series_id` points at it and `events.series_date` is the occurrence's place in the rule (it never changes when the event itself is moved). All three event columns and the table are additive and nullable: existing events don't repeat, and a client that doesn't know about series keeps working.
- **Exactly one occurrence per date.** A unique index on `(series_id, series_date)`, and every function that makes or re-plans occurrences first locks the series row (always series first, then events, so two callers can't deadlock). Making occurrences is `insert ... on conflict do nothing`, so whoever is second finds the date taken and makes nothing.
- **Kept filled by whoever opens the app, not by a job.** `topup_event_series()` makes every open series of the caller's workspace the occurrences it is missing for today in the team's time zone: every date within 8 weeks and never fewer than the next 2, nothing in the past (the first date, which the creator chose, may be) and no skipped date. Any signed-in member may call it (a candidate too): the app calls it after loading events, when the window comes back and every half hour, and only when its own copy of the events shows something missing. The earlier migrations only use pg_cron when it happens to be installed, so nothing here depends on it: a scheduled job could call the same function, but an idle team gets its occurrences as soon as anyone opens the app anyway. One series that can't be filled (for example its category was archived) is left and the others go on.
- **Generated occurrences are the series creator's.** `created_by` is set from the series, never from the caller, so they are editable by exactly the people who could edit them if the creator had added them by hand (the creator, a leader or moderator, a deputy: `may_edit_events()` repeats the policies on `events`), and not by whoever's browser happened to trigger the top-up.
- **Who may do what.** Making an event repeat (`make_event_repeat`), changing "this and following" (`update_event_series_following`) and deleting "this and following" (`delete_event_following`) need the right to edit the event, and every later occurrence it touches, exactly as today (the checks repeat the update and delete policies); a candidate adds no events at all. All of them are `security definer` with `search_path = ''`, check the caller's workspace first, are revoked from public and anon and granted to authenticated. `event_series` has row-level security with a read policy for the workspace and no write policy and no write privilege: a series is only made and changed by those functions, and never deleted by a client, so no history goes with it.
- **"This event" needs no function.** A plain update or delete of one occurrence works for old and new clients alike: a trigger remembers which columns an occurrence changed on its own (`events.series_overrides`; a later "this and following" edit from an EARLIER occurrence leaves exactly those fields alone, and one that starts at that occurrence overwrites them), and a trigger on delete keeps the date in `event_series.skipped` so it is never made again. A client can't set or clear those columns, make an occurrence by hand or move one between series; only the series functions can.
- **Re-planning.** Changing the date, Repeats or Ends "this and following" plans the later occurrences again from the chosen one on its new date: the series is split there (or changed in place when it was the first). Later occurrences that were never edited, have nothing on them (attendance, travel, shared costs, follow-up notes, a library talk, a chat post: `event_has_dependents()`) and are still ahead are dropped and made again by the new rule; everything else is never deleted: it stays in the series when its date still fits the new rule and is otherwise kept as a single event.
- **Moving an occurrence on the calendar.** Migration `20261116000100_move_event_occurrences.sql`, pgTAP `066_move_event_occurrences`, client `src/data/recurrence/move.ts` and `api.ts`. `move_event_one(event, date, end date)` ("Move just this one"): the occurrence leaves its series (`series_id`, `series_date`, `series_overrides` cleared) and becomes a single event on the new days, its old place is added to `event_series.skipped` so `series_fill` never makes it again; the length can't change. `move_event_series_following(event, days)` ("Move all"): this occurrence and every later one move by `days` and the rule moves with them: in place when it is the first occurrence, otherwise the series is split before it (the earlier ones keep the old series, which now ends the day before; a new series starts on the moved date with the same template, end and skipped places moved too). The moved events keep their ids, so answers, tickets, attendance and everything else on them stay; a place is counted along the rule (`series_slot_index`, `series_move_slot`), so a monthly rule keeps its own days and an event that no longer sits on its place gets `date` in `series_overrides`. Nothing is made or deleted: the next top-up fills what the moved series is missing. `restore_event_move(events, series, series to drop)` puts back the dates and series of the listed events, the rule (start, end, skipped) of the listed series that those events belong to, and deletes the listed series once nothing is in it. All three lock the series then the event (the order every series function uses), run `security definer` with `search_path = ''`, are granted to `authenticated` only, and need the right to edit every event they touch (`may_edit_events`: the creator, a leader or moderator, a deputy). The agent connector reads series, skipped dates and moved occurrences from the same columns as before; `supabase/functions/agent` did not change.
- **Deleting.** "This and following" deletes the chosen occurrence and every later one that is still ahead and stops the series just before it; later occurrences that are already over are history and stay as single events with their attendance; earlier ones are never touched.
- **Merging categories** (`merge_event_categories()`, replaced in the same migration) moves a series to the target category with its occurrences, without marking each as edited on its own.
- **Tests**: `030_event_series` (see the table below) runs the same table of date cases as `src/data/recurrence/cases.ts` (`rule.test.ts` checks that the two tables are identical) and shows the count per series date before and after repeated top-ups; `eventSeries.test.ts` fires twelve top-ups at the very same moment from three people, which is what a single pgTAP session can't do.

### Card tasks and notes

Each pipeline card, on both boards, has a checklist of **tasks** (a title, an optional due date and time, an optional assignee, ticked or not) and a running log of **notes** (who wrote what, when; never edited). Migration `20261108000100_card_tasks.sql`, pgTAP `051` and `052`, tools in "Agent connector". The app side (the done count, earliest due date, notes count and assignee on each card's face, the card panels, the profile's Pipeline card, Home's Today card) is built and the booked next step is removed from the app (see "What the app no longer uses"); a notification when a task is assigned to you is not built; the plan is [`plans/agent-connector-2026-11-14.md`](plans/agent-connector-2026-11-14.md), phase 4.

**Tables** (RLS on, default grants revoked, then `select, insert, update, delete` to `authenticated`):

- `card_tasks`: `id` (text, client-chosen or `gen_random_uuid()::text`), `workspace_id` (defaults to the caller's), the card as `person_id` (a prospect, recruiting board) **or** `entry_id` (a name on someone's list, customer board), exactly one of the two (a check), `title` (1 to 200 characters, trimmed), `done`, `done_at`, `done_by` (stamped by a trigger when a task is ticked, cleared when it is unticked, never taken from a client; `done = (done_at is not null)` is a check), `due_date`, `due_time` (wall-clock time in the team's time zone, `workspaces.timezone`, like `events.start_time`; a time needs a date, no time means due at the end of that day), `assignee_id` (a registered person: the card's owner, or whoever sets it; null means whoever owns the card), `position`, `created_by` (the caller, set by the trigger), `created_at`, `updated_at` (set on every update). The card's due date is not a column: it is the earliest due date among its open tasks.
- `card_notes`: `id`, `workspace_id`, `person_id` | `entry_id` (as above), `author_id` (the caller, forced by the trigger on a client write), `body` (1 to 2000 characters), `created_at` (now, on a client write). Insert and delete only.
- Why the rows point at the prospect or the list name and not at the stored card row: the board shows a card for every prospect and every list name, but a card has a stored row (`pipeline_cards`, `customer_cards`) only after its first move, and undoing that move deletes the row while the prospect stays on the board. A task keyed by the stored row could not exist for a card that never moved and would vanish on an undo. Keyed by the prospect (`people.id`) or the list name (`list_entries.id`), a task or note is deleted by cascade exactly when the card's subject is deleted (the person, or the name from the list, which also deletes the stored card), and the booking columns and the old note box of the stored card are neither read nor written by anything here.
- Writes by the database itself (a migration running as the table owner, with no signed-in person): `created_by`, `done_by`, `assignee_id` and `author_id` are nullable (null: the system), `created_at` and `updated_at` may be given, nothing needs a session, and the guard triggers skip their who-may-do-what checks for any writer that is not `authenticated` (the same way the other guards treat the seed and the database's own functions). A signed-in person is still held to every rule, and their `author_id` is forced to themselves.

**Who may do what.** The rules are the cards' own, copied from `pipeline_cards` ("read / edit cards of visible people": the prospect is in `visible_person_ids()` and the caller is not a candidate) and `customer_cards` (`list_entry_visible()`: the list's owner is in `visible_person_ids()`), with the same people for reading and editing; 051 proves the tasks and notes agree with the stored cards' policies for every actor.

| Actor                                                                                           | Recruiting board cards                                                               | Customer board cards | Tasks                                            | Notes                       |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | -------------------- | ------------------------------------------------ | --------------------------- |
| the card's owner (the prospect's sponsor, the list's owner)                                     | read, edit                                                                           | read, edit           | add, change, tick, delete; assignee: themself    | read, add; delete their own |
| an upline of the owner (leader included)                                                        | read, edit                                                                           | read, edit           | the same; assignee: the card's owner or themself | the same                    |
| the leader's deputy                                                                             | what the leader reads and edits (`visible_person_ids()` unions the leader's view in) | the same             | the same                                         | the same                    |

Not the same as customers: a customer person record is private to its owner (leaders included), but a name on the owner's list, and so its card, is visible to the owner's uplines. Other rules: the assignee, when set, must be the card's owner or the caller, and a registered person; a task cannot move to another card or team, and who made it and when cannot change; a note is added as the caller, with the real time. Anyone who can edit the card deletes its tasks; only a note's author deletes it. The conversion migration inserts rows as the migration role.

**Agent tools** run as the person under these same rules. They never create, move, book or delete a card, and never delete a task or a note; they never read the booking or the card's note box.

**Per-deployment steps** for a live project: (1) `npx supabase db push` (the new migrations `20261108000100_card_tasks.sql` and `20261109000100_card_followups_conversion.sql` are pending; the second converts the stored bookings and notes); (2) `npx supabase functions deploy agent --project-ref <ref> --use-api` (the function's registry now lists twenty tools; a function deployed before the migration makes the card tools fail until both are in place, and the migration before the function leaves the new tools unlisted); (3) nothing to set: no secret, no switch (the connector's existing `agents` switch and connection cover them); agents that paired earlier see the new tools on their next `tools/list` or `GET /tools`.

**What the app no longer uses (migration `20261109000100_card_followups_conversion.sql`, pgTAP `053`).** The app stopped booking a next step and keeping a single note on a card: it does not read or write `pipeline_cards` / `customer_cards` `next_column`, `next_step_date`, `next_step_time` or `note`, or `pipeline_step_cancellations`, and none of the rows it sends carries them (so a card edit cannot overwrite what is stored). The columns, the table and every shipped function stay, unchanged. `move_pipeline_card` and `move_customer_card` keep their booking parameters; the app passes none, so a booking that is already stored is **kept** when the card moves to a column before the booked one (or when the booked column no longer exists) and **cleared** when it moves into the booked column or past it (`booking_kept()`); undoing the move puts it back from `pipeline_moves.booking_before`. Nothing reads it either way. The migration copies what was stored, once: `convert_card_followups()` makes ONE open task on each card with a booked column (title: the column's name on the card owner's board from `board_columns()`, else the step's own label (a step hidden for the owner), else "Next step"; `due_date` and `due_time` from the booking, none when the booking had no day; assignee: the prospect's sponsor or the list name's owner; `created_at` the card's `updated_at`; `created_by` null) and ONE note on each card with a non-empty note (body trimmed, author the owner, `created_at` the card's `updated_at`), and never a task or note the card already has with the same content, so a second run makes nothing. It is revoked from every client role and returns `{tasks, notes}`; on a database with no bookings and no notes it makes nothing.

### Agent connector

A person can connect an AI agent of their choice (any agent that can make HTTP requests and keep a secret, with or without MCP) so that it manages their own and their team's data by conversation. It is on for a team by default: a team with no `feature_switches` row `agents` has it on, and a stored `enabled = false` row switches it off (migration `20261110000100_agents_on_by_default.sql`). Migrations `20261105000100_agent_connector.sql`, `20261105000200_agent_tools.sql`, `20261106000100_agent_people_tools.sql` and `20261108000100_card_tasks.sql`, Edge Function `supabase/functions/agent`, pgTAP `040`–`044`, `046`–`049`, `051`–`052`, `054` (on by default), integration test `agentConnector.test.ts`, plan [`plans/agent-connector-2026-11-14.md`](plans/agent-connector-2026-11-14.md) (phase 1: database, function and the first seven tools; phase 2: the Settings card and the leader's switch, no database change; phase 3a: the people and personal tools; phase 4: card tasks and notes).

**The flow.** A signed-in person presses a button (Settings, "AI agents") and `create_agent_pairing(p_access)` gives a one-time code, valid ten minutes, single use, for read or write access. They paste a short text with the connector URL and the code to their agent. The agent POSTs the code to `/pair` and receives its own opaque **connection key** (`crmak_` plus 43 characters, shown once; only its SHA-256 is stored). The person never handles the key and no username is involved. The key means something to one function only (the `agent` Edge Function); it is not a JWT and no other Supabase endpoint accepts it. An agent never holds a Supabase user token.

**What an agent can do** is the whitelist of SQL functions named `agent_*` in `public` (migration `…0200_agent_tools`). They are SECURITY INVOKER and run **as the person**, so the existing row-level security decides what they see and change. No deletes, ever; never stage, sponsor, IBO#/LTD# or the business start date.

**People and personal tools (phase 3a).** Contact fields follow vCard (RFC 6350), and every description says so in one clause: `full_name` (FN), `phone` (TEL), `email` (EMAIL), `location` (ADR locality and region as one text), `notes` (NOTE). Reads are as generous as the app: they show what row-level security lets the person see and add nothing. Writes are narrow and there are no deletes. **Never readable or writable through any tool:** the IBO number and the LTD number (no query selects them; pgTAP 047 looks for their values in every answer and every audit row). **Never writable:** stage (`biz_class`), sponsor, owner, `business_start_date`, `pipeline_stage`, `stage_history`, tags, monthly volume. `list_team` walks the sponsor line below the caller with ONE recursive query (`agent_private.team()`: the columns are carried along, so nothing is joined back; customers are not on the sponsor line), reading `people` as the caller, so the downline is exactly what row-level security shows. Stage is the effective one (`effective_biz_class()`: an apprentice past their first year is an IBO, as everywhere). Measured on a team of 300 in three levels (pgTAP 049's fixture, PGlite, the table analysed as a live database does): `list_team` about 17 ms a call, `whoami` 11 ms, the visibility helper 1 ms; one statement, no per-person query. Ordering is `lower(name)` in the database's collation after the level. An empty list says why in `note` (and what to do), so an agent does not retry. `get_person` writes the person's id and name to the audit row's `new_values`, where `add_prospect` writes its prospect, so the Settings activity list shows the name (marked sensitive like the prospect tools'). `whoami`'s `can` is two lists in the function; pgTAP 047 compares them with the catalog (every `agent_*` function; the read ones are those that start with `ctx(false)`), so a new tool that is not added there fails it.

**The shape of what tools return.** An agent should be a slightly more intelligent proxy than a script, so what a tool returns follows the standard of the service it will be copied into, with nothing left for the agent to guess: field names and meanings are the receiving standard's, and each tool's description names that standard and says what the receiver must do. For events the standard is iCalendar (RFC 5545), which Google, Apple and Outlook accept: `uid` is stable for the event's whole life, an all-day end is exclusive, a timed event carries its local wall-clock time with the team's IANA zone and the UTC instants worked out in SQL (`agent_private.zoned_instant`, right across daylight-saving changes, the repeated hour taken as the first, as the app's own `.ics` and RFC 5545 do), a repeating event is one `series` with an `rrule` and `exdates`, and an occurrence that was changed or moved on its own is an exception that names the slot it replaces (`recurrence_id`). The data comes from `agent_*` functions run as the person (audited, one row per call); turning it into text, as `export_events_ics` does, is formatting only and lives in the function folder. A new tool names its standard the same way (a task would be iCalendar VTODO). Contacts are vCard (RFC 6350): the people tools use `full_name` (FN), `phone` (TEL), `email` (EMAIL), `location` (ADR locality and region as one text) and `notes` (NOTE), a result's dates are ISO 8601, and a list says in `note` why it is empty.

**Repeat rules as RRULEs.** The RRULE of a series generates exactly the dates `series_nth_date()` generates: `daily` is `FREQ=DAILY`, `weekly` `FREQ=WEEKLY`, `biweekly` `FREQ=WEEKLY;INTERVAL=2`; `monthly_date` is `FREQ=MONTHLY;BYMONTHDAY=<day>` for days 1 to 28, `BYMONTHDAY=28,29;BYSETPOS=-1` for day 29 and `28,29,30;BYSETPOS=-1` for day 30 (the app's "last day of a shorter month"), and `BYMONTHDAY=-1` for day 31 (the app's rule for day 31 is the last day of every month, which `-1` says directly and every calendar reads); `monthly_weekday` is `BYDAY=<n><weekday>` for the first to fourth, and `BYDAY=-1<weekday>` for the fifth (the app falls back from a missing fifth to the last, so every month gets the last such weekday: the fifth where there is one, else the fourth). An end date is `UNTIL` as RFC 5545 requires for the series' start: a date for an all-day series, a UTC date-time (the last second of that day in the team's zone) for a timed one. Proof: pgTAP `046_agent_event_data` expands every form with an RRULE expander written from the RFC and compares the first 24 dates with `series_nth_date()` for every anchor day of 2027 and 2028; `series_nth_date()` is in turn tested against the shared case table (`src/data/recurrence/cases.ts`, pgTAP 030 and `rule.test.ts`).

**Timed repeating events in the file.** A timed series is written as `DTSTART;TZID=<zone>` with a `VTIMEZONE`, so it stays at the same wall-clock time across daylight-saving changes (an RRULE on UTC instants would drift by an hour). The VTIMEZONE is built in SQL from the database's own time zone data (`agent_private.zone_definition`): every offset change from the year before the series starts for 31 years must fall on the same month, weekday place (n-th or last), wall-clock time and offsets each year, and only then are the yearly rules written; otherwise (a zone whose clocks move on irregular dates, or one whose rules changed in that span) the series is written as separate UTC events for the window, never as a wrong repeat. Timed series that span more than one day are always sent as separate events, because RFC 5545 repeats an exact duration and the end would move by an hour across a clock change. Checked with an independent parser (`icalendar` and `recurring_ical_events` in Python): the file's VTIMEZONE agrees with the system zone database for every hour from 2025 to 2039, and the expanded series keep their wall-clock time.

**Tables** (all with RLS, default grants revoked). `agent_pairings` (hash of the code, who, access, expiry, used) and `agent_pair_attempts` (failed `/pair` attempts by hashed address, for throttling): no policy and no grant, reachable only through the `agent_private` functions. `agent_connections` (who, label, `key_hash`, access, created, last used, revoked): a person reads their own rows through a column grant that leaves out `key_hash` (the app names its columns, `select *` is refused) and revokes through `revoke_agent_connection(p_id)`; no client write. `agent_audit` (one row per call: tool, arguments, a result summary, old and new values of a write): a person reads their own rows only. Audit rows hold details of the people the agent touched, so the leader does not read her team's.

**The role `agent_connector`.** Created NOLOGIN, NOINHERIT by the migration; a deployment gives it a password and login outside the repository. It owns nothing and holds no table privilege. It can do exactly three things: look a connection up by key hash and touch `last_used_at` (at most once a minute); redeem a pairing code and record failed attempts (both are SECURITY DEFINER functions in `agent_private`, `search_path = ''`, executable only by it, plus `connector_refusal` for audit rows of refused calls); and `set role authenticated`. `agent_private` is not exposed by the Data API.

**How a call runs.** The Edge Function connects as `agent_connector` through the transaction pooler (secret `AGENT_DB_URL`, port 6543, `prepare: false`, a small lazy pool; without the secret every request answers 503). It looks the key's hash up, then runs ONE transaction: `select set_config('request.jwt.claims', <sub = the login, role authenticated>, true)`, `select set_config('app.agent_connection_id', <id>, true)`, `set local role authenticated`, `select public.agent_<tool>(...)`. Each tool starts with `agent_private.ctx()`, which refuses unless: the session was opened by `agent_connector` (`session_user`, which survives `set role`; an ordinary app session never has it), the connection is unrevoked and belongs to `auth.uid()`, it still matches that login's person and workspace, the person is still registered, the team switch is on (or the login is an app admin) and the access allows the tool (write tools need `write`). Turning the team switch off, revoking or demoting someone cuts an agent off on its very next call. A tool that understands but refuses a request (an update outside the caller's visibility, a bad answer) returns `{"error": ...}` after writing its audit row; one that raises rolls its own audit row back, so the function records the refusal itself (`connector_refusal`).

**Who may add an agent, and the preview rule.** `create_agent_pairing` refuses a login with no person record, a candidate and anyone who is not an apprentice, IBO or the team's leader (a deputy is an apprentice or IBO), and refuses while the team's switch is off (an explicit `enabled = false` row; no row counts as on, `coalesce(..., true)` in `agent_private.access_for`, the one function that reads the switch). An **app admin** (`app_admins`, see "Unlocks support") may pair while the team's switch is off. The database keeps this allowance for every admin, also one who is the team's leader or a deputy: for them the app hides the feature (`featureOnFor`: whoever can flip the switches sees a feature exactly when the switch is on), but an AI agent they already connected keeps working with the switch off, and `my_agent_access()` still reports `allowed` and `preview` for them. `my_agent_access()` tells the app whether the caller may use the feature and why not (`no_person`, `not_registered`, `switched_off`), for the Settings card.

**The function** (`supabase/functions/agent`). `POST /pair` (code + label in, key out; every refusal of a code, wrong, malformed, used, expired or switched off, is the same 403; 8 failures per hashed address in 10 minutes, 100 in all, give 429), `POST /mcp` (MCP over Streamable HTTP, stateless JSON; the server's name is the workspace's name in the database), `GET /tools` and `POST /tools/<name>` (plain HTTP for agents without MCP), all over one `runTool()`. No CORS headers and no browser client: any request that carries an `Origin` header is refused with 403 on every route, a request to `/mcp` whose `MCP-Protocol-Version` names a version the server does not support is 400, and a JSON-RPC response or notification sent by the client is answered 202 with no body. The logic is plain TypeScript over web-standard `Request`/`Response` with the database behind the `AgentDb` interface (`app.ts`, `tools.ts`, `ics.ts`, `pair.ts`, `mcp.ts`, `run.ts`, `pg.ts`), tested with vitest and a fake database; only `index.ts` is Deno-specific (and is left out of `npm run typecheck` because it uses the Deno globals; ESLint covers it). Errors: 401 unknown, malformed or revoked key (a malformed key never reaches the database), 400 invalid arguments (audited as a refusal, so is an attempt to change a field outside the whitelist), 403 refused (read-only connection, switch off), 404 unknown tool (not audited), 413 a body over 64 KB (the body is read to its end and thrown away before the reply: answering with the upload in flight left the gateway's connection hanging for the next request), 422 a refusal by the tool or by row-level security, 429 throttled, 503 not set up.

**Housekeeping.** `purge_agent_housekeeping()` removes used or expired pairings and old attempts after a day and audit rows after 180 days; it is scheduled with pg_cron like the chat retention (a notice when the extension is missing).

**Adding a tool.** One `agent_<name>` SQL function (SECURITY INVOKER, `search_path = ''`, starts with `agent_private.ctx(<writes?>)`, writes exactly one audit row, returns `{"error": ...}` for a refusal it understands) in a new migration; one entry in `supabase/functions/agent/tools.ts` (properties, description, whether it writes, the SQL and its parameters); tests: pgTAP for the function (who sees what, refusals, the audit row) and its name in the whitelist of `043_agent_catalog`, vitest for the entry (`tools.test.ts` fails when the registry and the migrations disagree).

**Switching the connector on for a team** (placeholders, no real values; never commit or print the secrets):

1. Apply the migrations: `npx supabase link --project-ref <ref>`, then `npx supabase db push` (the role is created NOLOGIN).
2. Give the role a password and let it log in: in the SQL editor, `alter role agent_connector with login password '<a long random password>';`
3. Set the function secret to the transaction pooler URL for that role. The pooler's username is `agent_connector.<ref>` (Dashboard → Connect → Transaction pooler shows the host and port 6543): `npx supabase secrets set AGENT_DB_URL='postgresql://agent_connector.<ref>:<password>@<pooler host>:6543/postgres' --project-ref <ref>`.
4. Deploy the function (it checks its own key, so the gateway must not demand a JWT; `config.toml` sets `verify_jwt = false`): `npx supabase functions deploy agent --project-ref <ref> --use-api`.
5. The switch is on by default (no row = on). To switch it off for a team: `insert into public.feature_switches (workspace_id, feature, enabled) values ('<workspace id>', 'agents', false) on conflict (workspace_id, feature) do update set enabled = false;` (Team settings has an "AI agents" switch for it, shown on until someone flips it). An app admin can try it while it is off.
6. Before anyone is given write access, make sure the project has backups you can restore from.

Without step 2 to 4 nothing is reachable: the function answers 503 until `AGENT_DB_URL` is set, and the role cannot log in until it has a password.

### Steps after Registered

A leader may add steps in a band after the Registered milestone (`pipeline_steps.band = 'registered'`, recruiting board only; `customer_steps` still refuses it). Migration `20261112000100_pipeline_steps_after_registered.sql`, pgTAP `058_post_registration_steps`, `059_post_registration_moves`, `060_post_registration_board`, Vitest `src/data/pipeline/afterRegistered.test.ts` and `afterRegisteredMutations.test.ts`. Everything a step has applies unchanged (the owner adds, names, orders and deletes their own, the downline inherits them uplines first, an inherited one can be hidden, the same name rules; deleting one sends its cards to Registered). Column order: Registered, the steps after it, then the outcome columns (`board_columns()` already ordered any band's steps after its milestone).

- **Moves.** `move_pipeline_card()` accepts a registered person (an apprentice or an IBO) and moves their card only between `registered` and the registered-band steps of the board that applies, in either direction. It never changes their class, stage history or start date and logs no registration; the move is a normal `pipeline_moves` row (band `registered`, `from_column` null when they had no stored card). Any other column is refused (`22023`, "A registered person moves only between Registered and the steps after it"), and so is "Already there" (a person with no stored card sits in Registered). A prospect still registers by moving into `registered`; a prospect cannot go to a step after it (`22023`). Same people as for a prospect: anyone who can see the person and is not a candidate (owner, uplines, deputies, and the registered person themselves, who sees their own card); a crossline gets "Person not found", a candidate `42501`.
- **Undo.** Deleting your latest move restores the card and removes the move only. `pipeline_moves_after_delete()` un-registers a person only when the deleted move is the one that registered them (their earliest move into the registered band).
- **Taking the card off the board** is an update of `pipeline_cards.dropped_at` (the same policy as for a prospect). A registered person's card that has no stored row is created in Registered by the policy "add the card of a registered person" (column `registered` only, never a step: that is a move).
- **Who is on the board after Registered** is judged on the person's SPONSOR's board by `pipeline_registered_card_column(person)` (the column, or null) and `pipeline_registered_in_progress(person)`, the mirror of `afterRegistered()` in `src/data/pipeline/afterRegistered.ts`: no registered-band step on the board = nobody (the board is as it was); a card taken off the board = not in progress; a card in a step is in progress, except in the board's LAST step (the finishing column) when it entered before the current month (finished); no card, a card in Registered, or a card in a hidden or deleted step shows in Registered only if the person registered on or after the cutoff, the 1st of the month (team zone) of the board's earliest registered-band step. Registered day: their earliest move into the registered band, else their business start date. Dates come from `workspace_today()` and the team's time zone. Both functions are `security definer`, executable by `authenticated`, and return null/false for a person the caller cannot see.
- **Tasks and notes.** `card_task_registered()` is about the ASSIGNEE (a task goes to the card's owner or the caller, who must be registered) and is unchanged. What refused a registered person's card was `card_tasks_guard()` ("Only a prospect has a card on the recruiting board"); it now lets a client insert a task when `pipeline_registered_in_progress()` says the card is in progress. The card policies (read and edit for people you can see, not candidates) never looked at the person's class, and `card_notes_guard()` never checked it, so notes needed no change. Ticking, editing and deleting tasks already on a finished card still work.
- **Agent connector.** `agent_private.card_lookup()`, `agent_private.card_docs()` and `agent_list_cards()` include registered people whose card is in progress, with their column id and name (`registered`, or the step's id and name); `get_card` and the task and note tools follow (`card_lookup`). They still cannot move a card, change a stage or delete anything. The tool descriptions in `supabase/functions/agent/tools.ts` say so (the Edge Function must be redeployed).
- **Your own card (migration `20261113000100_registered_own_card.sql`, pgTAP `061_registered_own_card`).** A registered person can see their own card (they are on their sponsor's board) but not change it: `move_pipeline_card()` raises 42501 for a registered person moving themselves (after the column checks, so a move that was never allowed fails for its old reason), and the policies "edit cards of visible people", "remove cards of visible people" and "add the card of a registered person" add `person_id <> current_person_id()`, so taking the card off the board, putting it back, deleting the row and creating it are all refused for the person themselves. The owner, an upline and a deputy are as before; a crossline and a candidate are still refused. Tasks and notes follow their own rules. A leader with no sponsor has no card, so nothing changes for them. The browser-storage mutations refuse the same (`no-access`).
- **Naming the step.** A registered person looking at their own card in a step used to get the right `column.id` and the name `Removed column` from `agent_private.card_docs()`: `board_columns()` shows a sponsor line only to people who can see its sponsor, and they cannot see theirs. `card_docs()` now falls back to the registered-band step's label, read from `pipeline_steps` (which the person can read for their own sponsor line). Only SQL changed: the Edge Function under `supabase/functions/agent/` is not touched.

### Event times

An event can have a start time and an end time. Migration `20261030000100_event_times.sql`, pgTAP `050_event_times`, integration test `eventTimes.test.ts`, client in `src/data/eventTimes.ts` (frontend guide: "Dates").

- **Stored as wall-clock time.** `events.start_time` and `events.end_time` are `time` (no zone), read as the time in `workspaces.timezone`; null = no time, and an event with no start time is all-day, exactly as before. The zone is not repeated on each event: a team has one, and a 7 PM session stays 7 PM when the clocks change. Whoever needs a point in time (the app's "Add to calendar", a program reading events) applies the workspace's zone to the event's date and time; the app loads the zone with the team (`fetchTeamLook`).
- **The rule** is `event_times_ok(length_days, start, end)`, a check constraint on `events` and `event_series`: an end time needs a start time, and on a one-day event the end is after the start; on a multi-day event the start belongs to the first day and the end to the last, so the end may be earlier in the day. `src/data/eventTimes.ts` has the same rule and both run the one table of cases in `src/data/recurrence/cases.ts`.
- **Repeating events carry the times.** `event_series.start_time` / `end_time` are part of what a new occurrence is made from: a new series takes the event's times, `series_fill` gives them to occurrences made later, and "this and following" changes them from that occurrence on. A time changed with "this event" is remembered like any other field (`series_overrides` gains `start_time` and `end_time`: the guard trigger's list, the following function's allowed fields and `SERIES_FIELDS` in `src/data/recurrence/plan.ts`; `fields.test.ts` checks the three agree). When an edit puts a time on an occurrence it does not fit (an end time with no start time, or an end not after the start on a one-day occurrence), that occurrence loses its end time; nothing is made up.
- **`events.updated_at`** (`timestamptz not null default now()`) is set by a `before update` trigger on every update, whatever a client sends, so a program reading events can tell what changed. Existing events start at their `created_at`. It is not shown in the app and not read by it.
- **Additive.** Nothing is dropped or tightened for a client that does not know about times: it writes no time column, its edits and its "this event" edits pass the guard as before, and it calls the same three series functions with the same arguments.

## Row-level security, in plain words

RLS is on for every table. Policies apply to signed-in users (`authenticated`), so an anonymous caller sees and writes nothing except the `get_invite` preview. Every rule below is limited to the caller's own workspace; a second workspace's rows are invisible.

**Workspace, members, invites**

- You read your own workspace, the team's look included. Leaders edit its name and timezone; nobody (leaders included) writes the look directly: `set_workspace_appearance()` is the only way, and only for the workspace leader (see [Team appearance](#team-appearance)).
- You always see your own member row. Chat users see the member list, and leaders see it too. Leaders add and remove members and designate moderators (change `role`).
- An ordinary invite can be created by anyone who isn't a candidate, for a sponsor they can see who is an apprentice or IBO. You see the invites you created or that name you as sponsor (leaders see all). The creator or a leader withdraws them. The app no longer offers a button for these; links already issued still work.
- An invite for an existing person (`person_id` set) can be created by anyone who isn't a candidate for someone they can see who is in their own downline, or by a leader or deputy acting as one (`can_invite_person()`); never for yourself, a customer or someone who already has a login. Everyone who may invite that person sees and withdraws their open invite, not only its creator.

**People and CRM data (the `access.ts` rules, now also on writes)**

- **People:** you read the people in `visible_person_ids()`.
  - Adding: you add business people under a sponsor you can see (leaders may add someone without a sponsor), and customers owned by someone you can see. Candidates add nobody. A sponsor or owner must be an apprentice or IBO.
  - Editing: you edit people you can see. Nobody changes their own stage or sponsor except leaders, and nobody can be re-sponsored under their own downline.
  - Deleting: you delete people you can see, except yourself. Their direct downline and customers move to their sponsor (see Triggers).
- **Customers are private:** you only ever see your own customers, never another person's, including your downline's. Leaders included.
- **Events:** everyone in the workspace reads all events. Anyone who isn't a candidate creates events. The creator, moderators, leaders and deputies edit or delete them. An event's category must be one of its workspace's (`23514`), and not archived when it's picked for a new event or a move (`23514`); an event in a category that's in person only is kept `in_person` (a `virtual` or `both` format is changed, like the app does before saving).
- **Event categories** (`20261016002000_event_categories`, mirror of `src/data/eventCategories`): everyone on the team reads them, archived ones too. Anyone who may add events adds one (not candidates; who made it and when are stamped, and it starts active). Only leaders and their deputies (`acts_as_leader()`) rename, change the icon, color or settings, reorder and archive or bring back; nobody deletes one. `merge_event_categories(from, into)` is leaders and deputies only (`42501`), both in your workspace (`P0002`), different (`22023`) and `into` not archived (`23514`); it moves the events (the trigger keeps them in person where needed) and archives `from` in one transaction.
- **Attendance and travel plans:** read and written only for people you can see, and only on your workspace's events (so uplines log their downline's attendance, and everyone their own).
- **Missed-event notes** (`20261014001000_event_types`, mirror of `src/data/eventTypes`): read by anyone who can see the person (the person included); written only by their uplines (`is_upline_of(person)`), or for a customer by the customer's owner or the owner's uplines (`is_customer_upline(person)`, `20261016002000`), never about yourself or an upline; `by_id` and `created_at` are stamped by the database; notes aren't edited, and only their author removes one. The follow-up rule itself runs in the app.
- **Shared costs:**
  - Everyone reads costs, cost memberships, overrides and payments (they're needed to work out each share).
  - Only leaders and (effective) IBOs create a cost, as its organizer, and the organizer is opted in automatically. Only the organizer (or a leader) edits or deletes it, and only a leader hands it to another organizer.
  - You opt yourself in or out; the organizer can opt in anyone they can see. Nobody opts out after paying.
  - Overrides are set by the organizer only, never on a paid share.
  - Payments are made only through `pay_sandbox()`.
- **Contacts, sales, learning, learning goals:** read and written only for people (or customers) you can see. Editing a learning entry in the app is an `update` of that row (the same `for all` policy; `learning_unit_fits_kind` is checked on the new kind and unit together), and deleting one is a `delete` of that row (the same policy; the app only offers it on your own entries, and Undo inserts the same id with its `created_at` again). Nothing in the database reacts to a deleted learning row: `library_progress` has no link to it, so when the entry came from finishing a library item (id `library:<item_id>:<person_id>`) the client also deletes that progress row and writes it back unfinished, which starts it unlogged (`logged_at` is never cleared by an update); on Undo the client inserts the entry first and then the finished progress row, whose `library_progress_log` trigger finds the entry there (`on conflict (id) do nothing`) and so logs no second row. A contact's `by_id` is you or someone you can see. Sales are also readable when they count toward someone you can see (`person_id`), so uplines can work out their team's PV; the customer's own row stays private to their owner. A sale counts toward the customer's owner, or the buyer for a personal order (`customer_id` is then a business person); `sales_attribute` fills `person_id` in and refuses anything else (`23514`).
- **Growth path** (`20261014000100_growth_path`, mirror of `src/data/growth`): `pv_overrides` (one per person and `YYYY-MM` month; replaces that month's logged PV) and `milestone_marks` (one per person and milestone code; `reached_on` not in the future) are read by anyone who can see the person and written only by their uplines (`is_upline_of(person)`: in your business downline, not a customer, not you). `set_by`/`set_at` and `marked_by`/`marked_at` are stamped by the database on every client write; the person, month and milestone of a row can't change. The milestone rules run in the app (permanent, live and monthly milestones; a hand mark is history only on live and monthly ones). `milestone_history` (`20261014010000_milestone_history`, one per person and milestone) keeps what the sponsor tree can forget: the first day a count milestone (First sponsor, 3/10, 6/25, 6/50, 12/100) was reached and the last day it was seen met, recorded by the app while the data shows it. Read like the marks; written by the person themselves or their uplines (not candidates); `recorded_by`/`recorded_at` stamped; an update keeps the earlier `first_reached_on` and the later `last_met_on` (so concurrent writers can't lose history); no dates in the future; no deletes from clients (the row goes with the person).
- **Contact settings, campaigns, report schedules:** your own only. Campaign recipients must be people you can see.
- **Activity:** you read entries about people you can see, or about no person (event-level entries). You add entries the same way. Nobody edits or deletes them.

**Chat**

- **Chat access:** chat is only for eligible people (apprentices, IBOs and leaders). A prospect, customer or candidate reads nothing, even with a stray membership row.
- **Reading:** you read conversations, members, messages, attachments, reactions and mentions only of conversations you belong to. **Nobody reads a DM they aren't in, leaders included.** You can also see (not read) the team chats you could rejoin, and groups you created.
- **Team chats:** every eligible member belongs to Announcements and Main chat, and is added to the pinned team groups (Daily wins, High signal) on joining. You may rejoin a team chat yourself.
- **Groups:** any eligible member creates one and becomes its `admin` (by trigger). Admins add people with any role and change roles. Group moderators add plain members. Only eligible people of the same workspace can be added. You can leave a group, but not Announcements, Main chat or a DM. When a group's last admin leaves, the longest-standing moderator (else member) becomes admin. Pinning a chat is for moderators and leaders.
- **Personal pins** (`conversation_members.pinned_at`): you pin and unpin chats in your own list only (like read state and mute, nobody changes someone else's, not even a group admin or leader). Joining a `pinned = true` team chat starts it pinned; adding someone to a group never pins it for them. At most 10 pins per tab (DMs, and everything else), `23514` beyond that.
- **Pinned message** (`conversations.pinned_message_id`): either member of a DM; in other chats whoever may moderate it (chat admins and moderators, workspace leaders and moderators). Group moderators may pin but not rename or otherwise edit the group. Only a message of the same chat can be pinned; removing it unpins it.
- **DMs:** created only through `create_dm()`, and only when `can_dm` allows it. You can't post in a DM once either side has blocked the other.
- **Posting:** you post as yourself, in your conversations. In Announcements only workspace moderators and leaders post directly; everyone else creates an `announcement_drafts` row.
- **Editing and removing messages:**
  - Authors edit their own messages (which stamps `edited_at`) and remove them.
  - Group admins and moderators, and workspace moderators and leaders, may remove other people's messages in any non-DM chat they're in. They can only remove (set `deleted_at`), never rewrite.
  - A removed message keeps no text or card; its attachment rows, reactions, mentions and pin are removed too.
- **Drafts:** authors see and edit their own pending drafts. Leaders and moderators see all drafts and review them with `approve_announcement` or `reject_announcement`.
- **Notifications:** only your own. Triggers and RPCs create them; you can only mark them read (`read_at`) or delete them.
- **Reports:** you report messages you can see. The reporter and the workspace leaders see the report. Leaders resolve it; moderators don't see reports. For a DM a leader isn't in, they see the report but never the message.
- **Blocks:** your own list. The blocked person never sees the block.
- **Library** (migration `20261013000300_library.sql`, mirror of `src/data/library/rules.ts`):
  - `library_can_see(workspace, created_by, visibility)`: the creator; everyone for `team`; IBOs (effective stage), leaders and moderators for `ibos`; the creator's business downline for `downline` (`library_upline_ids()`). Speakers, topics, sections and lessons follow their item or channel.
  - Sharing (`library_can_share`): leaders and moderators for any audience; anyone else with a business downline (not candidates) for `downline` only. Editing and deleting (`library_can_edit`): the creator or a leader / moderator. A guard trigger keeps `created_by`, `workspace_id` and `created_at`, and refuses widening the audience past what the editor may share.
  - Topics: everyone reads; leaders and moderators write.
  - Progress: your own rows only. The `library_progress_log` trigger logs finishing an item to `learning` once (id `library:<item_id>:<person_id>`, kind from `library_learning_kind`: documents `pages` × page count, workshops `workshop`, other audio/video `podcast`, other slides `pages`) and stamps `logged_at`, which clients can't set or clear. The app shows the same row at once (`serverSide`) and never writes it.
  - `library_channel_teasers()` lists the `ibos` channels you can't open yet (title, icon, color, lesson count); `library_people` (a view) names the speakers and creators of what you can see, for viewers whose CRM view and chat directory don't include them.
- **Pipeline** (migration `20261013000400_pipeline.sql`, mirror of `src/data/pipeline/rules.ts`):
  - The four milestones (`contact`, `first_meeting`, `first_plan`, `registered`) are codes, not rows, so nobody can rename, remove or reorder them. A step can't take a milestone's code or name, can't sit after Registered, and keeps its owner and band.
  - Steps, hides and team goals belong to one leader. Everyone on that leader's sponsor line below them reads them (that's the inheritance), and so does anyone who can see the leader (an upline viewing a downline leader's board). Only the owner adds, renames, reorders or deletes their steps and sets their goals. You hide a step only if it belongs to someone above you; your own you delete. Deleting a step sends the cards in it, anyone's, back to its milestone.
  - Cards: of prospects you can see. You edit the rating, where you met and "taken off the board"; the column and its entry time change only through moves (a guard refuses anything else). Candidates read no cards, not even their own (it carries their sponsor's notes).
  - Moves: you read the moves of prospects owned by people you can see (yourself and your downline). Only `move_pipeline_card()` writes them. You may delete your own latest move of a person within an hour (undo); the card goes back where it was, or away if that move created it.
  - Cancelled next steps (no longer used by the app; `pipeline_step_cancellations`, both boards; migration `20261014005000_pipeline_next_steps.sql`): read by whoever reads the card or the moves of its owner (so the numbers outlive the card); written by whoever edits the card, as themselves (`cancelled_by`), naming the card's real owner; you remove your own within the hour (undo); nobody edits one. Candidates have none. The booking and note on a card are plain card edits (same writers as the card).
  - Per-person numbers (`pipeline_stats_visible`): yours and your downline's, or anyone who shared with you. Crosslines and uplines never otherwise. A share only opens totals through `pipeline_person_counts()`, never the sharer's prospects or moves.
  - Shares: you read the ones you made and the ones made with you; you share your own (not with your uplines, who already see them) and revoke them. Requests: you read the ones you sent and the ones sent to you; you ask someone whose numbers you can't see yet (one pending request per pair; not candidates), withdraw a pending one, and the owner answers through `answer_stat_request()`.
  - `sponsor_chain(person)` answers only for yourself or someone you can see.
- **Your list and the customer pipeline** (migration `20261014000500_customer_pipeline.sql`, mirror of `src/data/customerPipeline/rules.ts` and the pipeline rules above):
  - List entries: you read and write the lists of people in `visible_person_ids()` (`list_owner_visible`): your own and your downline's, never a crossline's or an upline's; candidates have none. A list belongs to an apprentice or IBO (`can_own_list`). You add names as yourself (`added_by`); nobody moves a name to another list or changes its author; the customer link (`customer_id`) is written only by `move_customer_card()` (and cleared when that customer is deleted). A prospect link must be someone you can see.
  - Customer steps and hides: exactly like pipeline steps (`pipeline_team_row_visible`, owner writes, hide only an upline's step). The milestones (`contact`, `first_meeting`, `first_sale`, `on_ditto`) and fixed columns (`not_contacted`, `not_interested`, `do_not_contact`) are codes; a step can't take their codes or names (nor the retired `new_contact` / "New contacts"), can't sit after On Ditto, and keeps its owner and band. Deleting a step sends the cards in it back to its milestone.
  - Prospect check-in intervals (migration `20261115000100_checkin_intervals.sql`): four nullable columns on `pipeline_team_settings` (`checkin_hot_months`, `checkin_warm_months`, `checkin_cold_months`, `checkin_not_interested_months`), each 1 to 36, all four set or all null (one set always comes from one person). Same rows and policies as the team goals: the sponsor line and whoever can see the person read, a person writes only their own row, a candidate has none. Resolution is the nearest person up the caller's own sponsor line whose four are set, else the app's defaults (Hot 3, Warm 6, Cold 12, Not interested 12); the app does it client-side (`effectiveSettings`) and `public.my_checkin_months()` (security invoker, authenticated only) is the database's copy, zero rows meaning the defaults. No date is stored or compared: the app computes when a check-in is due from the team's day. pgTAP: `supabase/tests/064_checkin_intervals.test.sql`. The agent connector has no tool that reports who is due for a check-in or returns the contact settings, so none changed.
  - Cards: of entries you can see (`list_entry_visible`). The booked next step and note columns are stored but no longer used by the app (see "What the app no longer uses"); the column and entry time change only through moves (a guard refuses anything else). The only card you add yourself is one in `not_contacted` (a name on the list getting a next step).
  - Moves: you read the moves of lists owned by people you can see. Only `move_customer_card()` writes them. You may delete your own latest move of a name within an hour (undo): the card goes back (or away), a customer the move made is deleted again (their sales by cascade), a Ditto mark it set is cleared.
  - Customers stay private: a customer made from a downline's list belongs to that downline, so their upline sees the name on the list and the board but not the customer record or its sales.
  - Referred by (migration `20261016001600_referred_by.sql`, mirror of `src/data/referrals/rules.ts`): a prospect, customer or list name may name who referred them, a person (`referred_by`) or a name on a list (`referred_by_entry`), at most one. Whoever may edit the row may set it (the row's own policies), but only to someone they can see (`can_see_person()`) or a name on a list they can see (`list_entry_visible()`); the check runs only when the link changes, so an upline can still edit a downline's prospect who was referred by the downline's private customer. Nobody refers themselves. Deleting the referrer clears the link.
- **Directory:** `chat_directory` (a view) lists the names, stages and roles of the eligible members of your workspace, so chat screens can show authors outside your CRM visibility. It's empty for non-chat users.
- **Unlocks support** (migration `20261014001500_unlocks_deputies_admin.sql`, mirror of `src/data/team/rules.ts` and `src/data/access.ts`; what each person has unlocked by growth milestone runs in the app, `src/data/unlocks.ts`, so the UI gates pages and the database keeps limiting the data as above):
  - Admin flag (`app_admins`, keyed by auth user): you read only your own row; there is no insert, update or delete policy or grant for clients, so nobody makes themselves admin (the seed or the service role adds rows). `is_app_admin()` tells the app.
  - Deputies (`deputies`: leader, deputy, `added_by`, `added_at` stamped by the database): the leader and the deputy read the row. Only a workspace leader names their own deputies, and only an apprentice or IBO in their business downline (not themselves, not a prospect or customer). The leader removes a deputy, or the deputy steps down; a row never changes. A deputy sees and edits what the leader's view allows (people, contacts, attendance, lists, coaching the leader's team), edits and deletes events, and flips the team's switches; never the leader's customers, and never the leader's own owner-only rows (the leader's pipeline steps and goals, workspace branding, moderators).
  - Feature switches (`feature_switches`, one row per team and feature, no row = off, except `agents`: no row = on): everyone in the workspace reads them; leaders and their deputies add, flip and clear them (`updated_by`, `updated_at` stamped). Only `chats`, `library`, `campaigns` and `agents` have switches. Switches gate the UI; the chat and library tables keep their own RLS.
  - Feedback (`feedback`; the Feedback button, migration `20261016002500_feedback`): any member inserts a report for themselves (`person_id` and `workspace_id` default to the caller's and must match; no status, 1 to 2000 characters, a JSON object context under 8000 characters, a snapshot path only inside their workspace's folder). The sender reads their own reports; an app admin (`is_app_admin()`) reads every report in every workspace and changes only `status` (`new` or `done`, a column grant), nobody else reads one (leaders and uplines don't). No delete, and no edit of the text. `person_id` is set null if that person is deleted.

**Storage**

- `chat-media` (private): object paths start with the conversation id (the policies only check that first folder); the app uploads to `<conversation_id>/<uuid>.<ext>`. Members of that conversation read and upload; the uploader or a conversation moderator deletes. The app reads files through signed URLs (one hour).
- `library` (private, 200 MB per file; audio, video and PDF): the app uploads to `<workspace_id>/<item_id>/<uuid>.<ext>` before writing the item row. You read files of items you can see (by the item id in the path) and your own uploads; anyone who may share uploads into their workspace's folder; the uploader or the item's editors delete. Read through signed URLs (one hour). The local stack's global upload limit in `supabase/config.toml` is 200 MiB too (takes effect after `supabase stop && supabase start`).
- `feedback` (private, 512 KB per file; JPEG or WebP): the app uploads the page snapshot to `<workspace_id>/<feedback_id>.jpg` before inserting the report row. Any member uploads into their own workspace's folder; the uploader and app admins read; there is no update or delete policy. The admin page reads through signed URLs.

## Triggers

- **Guards (direct client writes only).** These stop clients changing columns they shouldn't:
  - ids, workspace and authors can't change;
  - `created_at` on messages, drafts, reports and reactions is always "now";
  - only a chat admin changes roles;
  - read state, mute and pins (`pinned_at`) are personal;
  - notifications only change `read_at`;
  - reports only get resolved;
  - you can't change your own stage or sponsor.

  RPCs and the seed run as the database owner and skip the guards.

- **Delete a person.** This mirrors `src/data/cascade.ts`:
  - Their direct downline and customers move to their sponsor.
  - Costs they organized pass to the sponsor, who isn't opted in.
  - Attendance, travel, cost memberships, overrides and payments go by foreign-key cascade.
  - Activity entries are written ("Moved under X (Y was removed)" and "Removed Y"), so the client should not log the delete itself.
- **Team chats.** When someone becomes a member, or later becomes eligible, they're added to Announcements and Main chat; on joining, also to the pinned team groups. A new group's creator becomes its admin. A new announcements, main or pinned chat gets every eligible member.
- **Notifications.** Nobody is notified about their own action, or by someone they've blocked. In a muted chat ("Mentions only") replies, wins and reactions don't notify.
  - A reply notifies the quoted author (`reply`). If the reply also mentions them, they get one notification, as a `mention`.
  - A post in Announcements notifies everyone else in it (`announcement_posted`; a mentioned member gets the `mention` instead). The author of an approved draft is also told by `approve_announcement` (`ref_id` = draft id).
  - Answering an event card notifies the card's author (`event_post`, through `answer_event_post`).
  - A mention notifies the mentioned member (`mention`).
  - A reaction notifies the message author (`reaction`, with `ref_id` set to the emoji).
  - A win card notifies the author's upline (sponsor chain) members who are in that chat (`win`).
  - A new announcement draft notifies every leader and moderator (`announcement_draft`, with `ref_id` set to the draft id).
  - A report notifies every leader (`report`, with `ref_id` set to the report id).
  - A request to see someone's pipeline numbers notifies them (`stat_request`, `ref_id` = request id); withdrawing it removes that notification. The answer notifies the requester (`stat_request_answered`, through `answer_stat_request`).
- **Pipeline.** Deleting a step moves its cards back to the step's milestone; undoing a move puts the card back (with the booking it had before the move) (and undoing a registration makes the person a prospect again); cards' columns and steps' owner and band are guarded (see the RLS section).
- **Customer pipeline.** The same for customer steps and cards; undoing a move also deletes a customer it made and clears a Ditto mark it set. A name's owner, author, creation time and customer link are guarded.
- **Cancelled next steps.** A cancellation writes an activity entry about the person ("MG1 cancelled · No-show", id `stepcancel-<id>`, the prospect, or the customer / prospect behind a list name); removing the cancellation (undo) removes it.
- **Conversation check-in.** This is the contract rule. When A posts in a DM and B posted in that DM within the previous 24 hours, the database records one `contacts` row for each direction, with `source = 'message'`, dated the local day in the workspace's `timezone`. In a group, the same happens when A replies to B and B, within the previous 24 hours, replied to one of A's messages. It happens at most once per pair per local day. Both people get a `checkin_logged` notification whose `ref_id` is the contact about the other person. A single "hey" to everyone, or messages in one direction, never count.
- **Retention.** `purge_expired_messages()` deletes messages older than their conversation's `retention_days`. pg_cron runs it nightly at 03:17 (job `purge-expired-messages`). Clients can't call it.

## Realtime

The `supabase_realtime` publication includes `messages`, `reactions`, `mentions`, `attachments`, `notifications`, `conversation_members`, `conversations`, `announcement_drafts` and `reports`. Subscribers only receive rows their RLS lets them read (deletes carry only the primary key).

## Seed

`supabase/seed.sql` is generated by `scripts/db/generate-seed.ts`. Don't edit it by hand. The generator reads:

- the CRM demo seed (`src/data/seed.ts`);
- the chat demo seed (`seedChat()` in `src/data/chat/seed.ts`): workspace `w1`, the four pinned team chats, the Fall Weekend carpool group, DMs, the event, win, learning and link cards, reactions, the mention of Maria, Sarah Kim's pending announcement draft, a reported spam message, two library items, notifications and read state;

- the pipeline demo seed (`seedPipeline()` in `src/data/pipeline/seed.ts`): Maria's nine steps, Anita's "3-way call", David hiding Info 3, a card for every prospect, about 3,900 moves over six months (history moves of prospects who have since left the CRM keep `x…` person ids), team goals, Marcus's share with Anita and three stat requests (their notifications come with the chat seed, so the request trigger is off while they load);
- the customer pipeline demo seed (`seedCustomerPipeline()` in `src/data/customerPipeline/seed.ts`): Maria's three customer steps, lists for Maria, Anita, David, Jamal, Marcus and Tasha with their cards and moves (names at First sale / On Ditto link to the existing customers c1–c8 and c11, whose `ditto_since` comes from `seedPeople()`), and six months of history moves for names no longer on a list (`xl-…` entry ids);

The database therefore holds exactly what the browser demo shows. Dates are written relative to the reset time (`seed_tmp.d(n)` and `seed_tmp.ts(seconds)`). The same script generates `supabase/tests/001_visibility_parity.test.sql`. It runs `access.ts` over the seed for each demo user and asserts that RLS returns exactly the same people, customers and attendance rows, and the same contact, sale, learning, pipeline card and pipeline move counts, list entries, customer card and customer move counts.

## Moving to hosted Supabase

1. Create a project at supabase.com. In Database → Extensions, enable **pg_cron** first so the retention job gets scheduled. Without it, the migration only prints a notice and you'd schedule `select public.purge_expired_messages()` yourself.
2. Link the project and push the migrations. `db push` doesn't run the seed, and the seed's demo logins must never go to a real project.
   ```
   npx supabase login
   npx supabase link --project-ref <project-ref>
   npx supabase db push
   ```
3. Auth settings (Authentication → URL configuration): set the site URL to the deployed app and add its `/auth/callback` redirect. Configure SMTP (Authentication → Emails) for magic links and invites; the built-in sender is heavily rate-limited.
4. Create the first workspace and leader in the SQL editor. Sign up the leader first, then:
   ```sql
   insert into public.workspaces (id, name) values ('w1', 'Demo Team');
   insert into public.people (id, workspace_id, name, email, biz_class, pipeline_stage, business_start_date)
   values ('1', 'w1', 'Leader Name', 'leader@example.com', 'ibo', 'ibo', current_date);
   insert into public.members (workspace_id, person_id, user_id, role)
   select 'w1', '1', id, 'leader' from auth.users where email = 'leader@example.com';
   insert into public.conversations (workspace_id, kind, title, icon, pinned, created_by) values
     ('w1', 'announcements', 'Announcements', 'megaphone', true, '1'),
     ('w1', 'main', 'Main chat', 'users', true, '1'),
     ('w1', 'group', 'Daily wins', 'trophy', true, '1'),
     ('w1', 'group', 'High signal', 'sparkles', true, '1');
   ```
   Everyone else gets a login through an invite: add them as a person, then invite them from their profile (`accept_invite` attaches the login to that record). Links issued earlier by the removed "Invite someone" button still work.
5. Build the app with `VITE_DATA_SOURCE=supabase`, `VITE_SUPABASE_URL=https://<ref>.supabase.co` and `VITE_SUPABASE_ANON_KEY=<anon or publishable key>`, for example as CI secrets. Never put the service-role key in a `VITE_` variable. The GitHub Pages demo keeps `VITE_DATA_SOURCE=local`.
6. After any schema change: add a new migration, `npm run db:reset`, `npm run db:test`, `npm run db:types`, then `npx supabase db push`.

## Known gaps and decisions

- **One workspace per user for now.** `current_workspace_id()` picks the first workspace joined. Switching workspaces needs a choice passed per request, such as a JWT claim, when multi-team arrives.
- **`current_member_role()`** stands in for the `current_role()` named in the brief, because `current_role` is reserved in SQL.
- **Chat child tables have no `workspace_id`.** They follow the contract exactly, and isolation comes from their conversation or person.
- **The seed mirrors the browser demo, not the triggers.** For example, the demo's `checkin_logged` notification for Maria and Anita has no matching `contacts` row, and the High signal reply exchange between Maria and Jamal would count as a check-in if it were posted live. Change `src/data/chat/seed.ts` and re-run `npm run db:reset` to change the seed.
- **Pinned message per chat** is `conversations.pinned_message_id` (an addition to the contract; the browser store's `Conversation.pinnedMessageId`).
- **Seed media aren't real files.** Seed attachments use `seed:` storage paths, which the client synthesizes, and seed library items use `seed:audio:`, `seed:video:` and `seed:pdf:` paths that the client generates. Real uploads must follow the bucket path rules above.
- **`event_post`** means "someone answered your event card" (that's how the inbox shows it), so it comes from `answer_event_post()` after the RSVP rather than from a trigger on posting. Event card totals come from `event_rsvp_counts()`.
- **Retention and storage.** The nightly purge deletes expired messages (and their attachment rows by cascade) but not the files in `chat-media`; a storage cleanup job is still to do.
- **Team chat ids.** The seed keeps readable ids (`main`, `daily-wins`, …); a hosted workspace's are generated. The app finds team chats with `getTeamChatId()`.
- **Activity rows and `stage_history` are still written by the client**, as today. The database writes activity only for person deletes and invite sign-ups.
- **Reported DMs.** Leaders see the report and the reason, never the DM text. Moderation of DMs is therefore limited, by design ("nobody reads DMs").
- **No "no DMs" setting.** It's possible later, as the plan says. Report and block are in place.
- **Dates.** "Local day" for check-ins uses the workspace `timezone` (America/Chicago in the seed). `effective_biz_class` uses the database's `current_date` (UTC), so an apprentice's promotion can show a few hours early or late.
- **Payments only through `pay_sandbox()`.** There is no direct insert, so amounts can't be forged.
- **Opening a DM and posting are separate requests.** Inserting a message with `create_dm()` inside the same SQL statement fails RLS, because the new membership isn't visible yet within that statement.
- **Push notifications, SMS sign-in and media transcoding** are later phases.
- **Unlocks are UI gating.** Growth milestones run in the app (unlocks go by milestones ever reached, kept in `milestone_history` and hand marks once the tree no longer shows them), so the database doesn't enforce who reached First sponsor or 3/10: anyone who isn't a candidate can still add events and event categories through the API, and the recruiting tables follow visibility, not milestones. Feature switches likewise only hide the UI; the chat and library tables keep their own rules.
- **Who made an edit.** Recorded today: `contacts.by_id`, `activity.actor_id` (client-written entries for most CRM edits), `pipeline_moves.moved_by`, `customer_moves.moved_by`, `pv_overrides.set_by`, `milestone_marks.marked_by`, `milestone_history.recorded_by`, `missed_event_notes.by_id`, `list_entries.added_by`, `events.created_by` and `event_categories.created_by` (creation only), `deputies.added_by`, `feature_switches.updated_by`. Not recorded on update: people, events, attendance, travel, shared costs, card next steps, list entry edits and learning goals carry no "updated by" column, so a deputy's edit there is only traceable through the activity entry the app writes (where it writes one). Adding `updated_by` stamps to those tables is the follow-up.
- **Feedback**: the sender's name is saved in the report's `context` (`senderName`), because an app admin may not be allowed to read that person's row. A snapshot whose report insert failed for good stays in the bucket (senders can't delete); a retry of the same report reuses it. Reports have no retention or cleanup yet.
- **Deputies in the browser demo** don't check that the leader is still a leader (the database does).
